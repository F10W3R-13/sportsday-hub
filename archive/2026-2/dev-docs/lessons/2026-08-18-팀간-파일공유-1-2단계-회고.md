## 핵심 교훈 (한 줄)

**"집중화된 뷰"가 문제의 본질이었다** — 데이터(누가·언제·무엇을)는 이미 다 있었고, 각 팀 페이지를 일일이 방문해야 한다는 구조만 없애면 됐다. 그리고 main 푸시는 곧 배포이므로 마이그레이션 적용은 "사용자가 성공했다고 말한 것"이 아니라 OpenAPI로 직접 검증해야 한다(이번에 0013을 잘못 실행한 사례 — `if not exists`가 구해줬다).

## 무엇이 만들어졌나 (다음 세션의 출발점)

### 1단계 — 전체 팀 파일 피드 (main 배포 완료)

- 대시보드 '📁 최근 파일 활동' 위젯(전체 팀 8건·NEW 배지 72h·팀 색 배지·수정자·timeAgo) + `/files` 전체 페이지(`?team=` 필터칩·수동 동기화)
- 페이지 진입 시 백그라운드 자동 동기화 — **8/9 스펙에만 있던 "5분 신선도"를 마침내 구현** (60초→5분, `skipped` 플래그)
- `drive_files.created_time` 캡처(마이그레이션 0013, 사용자 적용 + force 동기화로 백필 5팀·29파일)
- 휴면 activity-feed 코드 삭제 + `timeAgo` 유틸 추출
- 첫 NEW 배지 사례: "카드뉴스 홍보부 인계물.docx" (heesupri1022, 8/18)

### 2단계 — 인계 추적 handoffs (main 배포 완료)

- `handoffs` 테이블(마이그레이션 0014, 시드 5건): 주는 팀 → 받는 쪽(**5팀 + 외부 조직** "홍보부" 등, 상호배타 CHECK), 제목, `due_date`(자체 컬럼 — 마일스톤 조인 기각), 완료 2단계
- 대시보드 '🤝 인계 현황' 위젯(urgency순 — **지연 빨강/임박 3일 주황** 배지, 주는 팀 최신 파일 **자동 힌트**, 체크리스트 딥링크 `?tab=checklist&focus=` 재사용)
- `/handoffs` 관리 페이지: 등록·편집 다이얼로그(from≠to 검증), optimistic 완료 토글, 소프트삭제, `?to=` 필터(팀+외부)
- 시드 5건이 실제 인계 사례 그대로: 물품 리스트(content→budget, 8/16 지연), 카드뉴스 안내, 홍보부 1·2차(8/18·8/30), 버스 명단

## 백엔드/데이터 설계 결정 (왜 이렇게 됐는지)

- **인계는 독립 엔티티** — 체크리스트의 "→ 예산팀 인계" / "수령" 두 항목을 하나의 계약으로 모델링. 기각: 체크리스트에 인계 필드 추가(1계약 2중 기입), 텍스트 파싱(오탐·조용한 누락)
- **이벤트 로그(접근법 B) 기각** — 5팀·수십 파일 규모에서 과설계. 필요해지면 위젯·쿼리 UI 재사용해 확장
- **기한은 마일스톤 조인이 아닌 자체 `due_date`** — "홍보부 인계 8/18, 8/30"처럼 회의와 무관한 기한이 존재
- **완료 자동 추정(파일명 매칭) 기각** — 자동 힌트(주는 팀 최근 파일 표시)만, 완료는 사람이
- `audit_log`에 `team_id` 컬럼이 없다 — 감사 트리거는 기존 5테이블과 동일하게 미기록. `updated_at` 자동갱신 트리거도 없다 → **토글·편직 mutation이 `updated_at`을 명시 갱신** (완료 정렬이 최근순이라 필수)

## 배포/프로세스 교훈

1. **마이그레이션 검증은 보고가 아니라 관찰로** — 사용자가 "성공"이라 한 SQL이 1단계 것(0013)이었다. PostgREST OpenAPI(`GET /rest/v1/` definitions)로 테이블 존재를 직접 확인하는 것이 유일한 진실. 이제 이 검증 패턴을 확보함.
2. **조회 하나가 페이지를 죽이지 않게** — 로컬 스모크에서 `getDriveConnectionStatus()` 내부 복호화 throw가 대시보드를 500로 죽였다. page 레벨 `.catch` 폴백(미연결/빈 배열 취급)으로 3곳(대시보드·/files·/settings) 정비. 컴포넌트 테스트 인프라가 없어 **수동 스모크가 유일한 검출망**이었다.
3. **배포 순서** — main 푸시 = Vercel 즉시 배포. DDL 마이그레이션은 항상 푸시 전 적용. (0014 미적용 시 /handoffs 500 — 대시보드는 `.catch(() => [])` 빈 폴백으로 설계됨)
4. **SDD 프로세스 실효** — 서브에이전트 13개 태스크 전부 1차 리뷰 통과, 픽스 루프 1회(위 폴백). 구현자들의 "브리프 이탈" 6건은 전부 **계획 문서의 버그**(mock 체인 불일치, `DriveFile['Insert']` 불가 타입, TeamId 좁힘 필요, Base UI Select 시그니처, React Compiler lint) — 계획 코드도 타입체크 수준의 검증이 필요하다는 신호.
5. **사용량 한도로 태스크 중단** → ledger 기반 재개(부분 산출물 대조·완성)로 무손실 복구. ledger의 가치를 실감한 세션.

## 사용자 병목 / UX 관찰

- 시드 8/16 물품 리스트가 **지연 배지로 바로 보임** — 의도된 첫 화면. 이미 전달 완료라면 `/handoffs`에서 완료 체크 필요(사용자 액션)
- 닉네임 다이얼로그 트리거가 유실 상태(`useNicknamePrompt` 호출자 없음) — 감사 로그가 '익명'으로 쌓일 수 있음 (기존 이슈, 이번에 미처리)
- 타임존: urgency가 런타임 로컬 자정(Vercel=UTC) 기준 — KST 사용자의 00:00~09:00 사이 지연 판정이 최대 9시간 늦어짐 (기존 `milestones-urgency` 관례 공유, 신규 회귀 아님)

## 내 코드의 한계 (솔직 회고)

- **계획 문서 버그 6건**이 구현 단계에서 발견됐다 — 계획에 "완전한 코드"를 싣는 방식은 그 코드가 컴파일되지 않으면 반쪽짜리다. 계획의 코드 블록은 최소한 타입·mock 체인 정합은 머릿속 tsc로 검증했어야.
- optimistic `overrides`에 **실패 롤백이 없다** — 토글 실패 시 거짓 체크가 잔류하고 서버 값을 계속 덮어쓴다 (3줄 수정 가능, 후속 1순위).
- `handoffDirectionLabel`이 **구현·테스트만 하고 미사용** (스펙이 요구했으나 UI는 인라인 렌더).
- 스펙 "미완료 6건" vs 구현 "정렬 후 상위 6건"(미완료 부족 시 완료가 슬롯 채움) — 문서와 코드 어느 쪽도 통일 안 됨.
