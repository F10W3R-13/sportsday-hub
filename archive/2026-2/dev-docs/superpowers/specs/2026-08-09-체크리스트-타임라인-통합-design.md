# 체크리스트·타임라인 통합 — 설계 문서

**작성일**: 2026-08-09
**대상**: 26-2 스포츠데이 허브의 체크리스트를 타임라인(마일스톤) 아래로 통합
**상태**: 승인됨 (설계 단계 완료)

---

## 0. 배경

현재 앱에는 두 개의 분리된 뷰가 있다.

- **체크리스트** (`/checklists`): `section`(progress/feedback/prep) + `team_id`로 그룹핑. `sort_order`만 있고 **시간 정보가 없다**. 항목 텍스트가 요약돼 있어 담당자에게 바로 와닿지 않고, 시간순 정렬도 안 돼 있다.
- **타임라인** (`/timeline`): 마일스톤이 날짜순(월별 그룹핑)으로 표시. 체크리스트와 연결고리 없음. 체크박스는 `disabled`.

**핵심 통찰**: 체크리스트 항목 텍스트가 이미 날짜/마일스톤 정보를 품고 있다 ("준비물 주문 (9/3)", "게임 물품 리스트 수령 (컨텐츠팀 8/16 완성 후)" 등). 두 데이터는 사실 같은 시간 축 위에 있다. 마일스톤을 상위 구조로 두고 체크리스트를 그 아래 매달면 시간순 정렬 문제가 자연스럽게 풀린다.

**대전제**: 사용자(하클 팀원)는 AI나 기술적 요소를 모르는 일반인이다. "지금 내가 뭘 해야 하는지"가 한눈에 들어와야 한다.

## 1. 요구사항 요약

브레인스토밍을 통해 확정된 요구사항:

| 항목 | 결정 |
|---|---|
| 시점 모호 항목 처리 | `milestone_id = NULL`인 '상시' 버킷으로 분리 |
| 페이지 통합 | 체크리스트 탭 제거, 타임라인 탭으로 단일 통합 |

| 체크리스트 없는 마일스톤 | 마일스톤 자체가 체크 가능 항목 (`disabled` 제거) |

## 2. 데이터 모델

### 2-1. 스키마 변경 (`checklist_items`)

```sql
-- section 컬럼 제거
ALTER TABLE public.checklist_items DROP COLUMN IF EXISTS section;

-- milestone_id FK 추가 (nullable: NULL = 상시 버킷)
ALTER TABLE public.checklist_items
  ADD COLUMN IF NOT EXISTS milestone_id uuid
  REFERENCES public.milestones(id) ON DELETE SET NULL;

-- 인덱스 (마일스톤별 조회 빈도 high)
CREATE INDEX IF NOT EXISTS idx_checklist_items_milestone_id
  ON public.checklist_items (milestone_id);
```

**참고**: `ON DELETE SET NULL` — 마일스톤이 삭제돼도 체크리스트 항목 자체는 상시 버킷으로 남는다 (데이터 손실 방지).

### 2-2. 마이그레이션 파일

새 마이그레이션 `0008_checklist_milestone_integration.sql`:

1. 위 스키마 변경 (`section` 제거, `milestone_id` 추가, 인덱스)
2. **시드 데이터 재매핑**: 기존 `checklist_items` INSERT 문의 `section` 컬럼 제거 + `milestone_id` 값 채우기
3. 기존 `0005_seed_data.sql`의 체크리스트 시드 섹션은 그대로 두되(이미 `ON CONFLICT` 안 씀 — `DELETE` 후 `INSERT`), 새 마이그레이션에서 전체 재정의

### 3-2. 마일스톤 카드 — 두 가지 모드

**A. 하위 체크리스트가 있는 마일스톤**

```
☐ 8/16 (토) [산출물] 컨텐츠 완성 (1/4)   [컨텐츠]  ▼
  └ ☐ 게임 물품 리스트 수령              [예산]
  └ ☐ 토너먼트 4종 확정                 [컨텐츠]
  └ ☐ 메인게임 2종 확정                 [컨텐츠]
  └ ☐ 미니게임 6종 확정                 [컨텐츠]
```

- 마일스톤 체크박스: **비활성** (하위 완료율로 자동 산출 — `(1/4)` 표시)
- 펼치기/접기 토글(▼) — **기본 펼침**
- 마지막에 하위 진행률 `(완료/전체)`

**B. 하위 체크리스트가 없는 마일스톤**

```
☐ 8/13 (수) [산출물] 타임라인 완성       [타임라인]
```

- 마일스톤 체크박스: **활성화** (사용자가 직접 체크 가능 — 기존 `disabled` 제거)
- 토글 없음
- 마일스톤 자체가 하나의 체크리스트 항목처럼 동작

### 3-3. 하위 체크리스트 렌더링

- 마일스톤 라인보다 **들여쓰기** (`└` 인디케이터 + 좌측 padding)
- `EditableChecklistCheckbox` (기존 컴포넌트 재사용) — 체크 토글 즉시 반영
- `PriorityBadge` (기존 컴포넌트 재사용)
- 팀 배지는 체크리스트 자체의 `team_id` 사용 (마일스톤 팀과 다를 수 있음 — 예: 8/16 컨텐츠 완성 마일스톤 아래 예산팀 체크리스트)

### 3-4. '상시' 버킷

- 위치: 월별 그룹 **이전(페이지 맨 액팅)**
- 헤더: "⚙ 상시 / 특정 시점 없음"
- `milestone_id IS NULL`인 체크리스트 항목들
- 마일스톤 날짜 기반 그룹핑이 아니라 **팀별 서브그룹핑** 적용 (상시 항목은 팀 컨텍스트가 더 중요)
- 체크 가능 (일반 체크리스트 항목과 동일)

### 3-5. 필터

기존 `UnifiedChecklist`의 `all/incomplete/complete` 필터를 타임라인 전체로 확장:

- `전체`: 모든 마일스톤 + 체크리스트 표시
- `미완료`: `completed = false`인 항목만 (마일스톤 + 체크리스트 모두에 적용)
- `완료`: `completed = true`인 항목만

체크리스트 + 마일스톤 **모두**에 필터 적용. 단, 빈 마일스톤(조건에 맞는 하위가 없는)은 표시하지 않음.

### 3-6. 전체 진행률

페이지 상단 프로그레스 바: `(체크리스트 완료 수 + 체크 가능한 마일스톤 완료 수) / 전체 항목 수`.

하위 체크리스트가 있는 마일스톤은 진행률 계산에서 "마일스톤 1개"가 아니라 "하위 항목 N개"로 카운트.

## 7. 리스크 & 고려사항

1. **시드 재매핑의 정확성**: 일부 체크리스트 항목은 마일스톤 추론이 주관적일 수 있다. 구현 시 매핑 표를 명시적으로 작성하고 1차 검증 후 PR.
2. **기존 감사 로그**: `section` 값이 변경되는 것이라 감사 트리거에 영향 가능. `0003_audit_softdelete.sql`의 `trg_audit_checklist_items`가 `old_value/new_value`에 `section`을 기록하고 있을 수 있음 — 스키마 변경 후에도 기존 로그는 JSON으로 남아있으므로 호환성 문제 없음 예상.
3. **하위 체크리스트 완료율 → 마일스톤 자동 완료 여부**: 하위 항목이 모두 완료되면 마일스톤을 자동으로 완료 처리할지 결정 필요. **이번 설계에서는 자동 완료 미구현** (마일스톤은 독립적으로 관리). 추후 기능으로 고려.
4. **팀 페이지의 체크리스트 패널** (해결됨): `components/team/checklist-panel.tsx`가 팀 상세 페이지(`/team/[id]`)에서 `section` 기반으로 동작 중. `useAddChecklistItem` 뮤테이션도 `section`을 필수 파라미터로 받음. **둘 다 `milestone_id` 기반으로 함께 수정** (§4-2, §6에 반영).
