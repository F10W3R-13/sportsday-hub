# 체크리스트 항목 텍스트 다듬기 — 설계 문서

**작성일**: 2026-08-09
**대상**: 26-2 스포츠데이 허브의 94개 체크리스트 항목 텍스트 개선
**상태**: 승인됨 (설계 단계 완료)

---

## 0. 배경

앞선 작업(체크리스트·타임라인 통합)에서 마일스톤 아래 체크리스트가 트리 구조로 표시되도록 구조를 개선했다. 하지만 **체크리스트 항목 텍스트 자체**는 기획팀 내부용 줄임말·참조 기호·작년 참고 주석을 그대로 품고 있어, 담당자가 봐도 무슨 말인지 모르는 항목이 많다.

**문제 예시:**
- `컨셉(D1)·팀 개수(D2) 수령` — D1, D2가 뭔지 모름
- `각 게임별 상세 시트 작성 (양식 §3)` — §3이 어디 문서의 3절인지 알 턱이 없음
- `율전 브룸에 물품 미리 비치 (26-1: 명륜 브룸 부재로 당일 혼란)` — 할 일과 작년 참고가 뒤섞임
- `입장료 결정 (D4, 8/16~8/25 — 보전 한도 파악 후)` — "보전 한도"가 전문용어

이 작업은 **구조가 아니라 내용**을 개선한다.

## 1. 요구사항 요약

브레인스토밍을 통해 확정된 요구사항:

| 항목 | 결정 |
|---|---|
| 작년 참고/교훈 | content에서 제거, source 필드로 분리 |
| 참조 기호(D1, §3, 종속, 보전 한도 등) | 자연어로 풀어쓰기 |
| 팀 내 줄임말(25-2, 하클, 율전, 명륜 등) | 유지 |
| 작업 방식 | 1차 변환(최소 수술 원칙) → 검증 → 사용자 검토 → DB 반영 |

## 2. 핵심 원칙: 최소한의 수술

> **원본 문장을 최대한 그대로 보존한다. 진짜 안 되는 것만 손댄다.**

이전 접근("다듬기/재작성")에서 발생한 문제:
- 정보 손실 ("최소 3일 전" → "3일 전" — 뉘앙스 상실)
- 오타 ("불고기버거" → "불고아버거")
- 확정을 참고로 착각 (탑앤탑/12,400원을 content에 단정적으로)
- 고유명사 훼손 (SG MAPLE → 정규 교환학생)

이를 방지하기 위해 원칙을 수정했다.

### 규칙 A — content(할 일) 정제: 최소 변경

**허용되는 변경 (이것만 손댄다):**
1. **참조 기호 → 자연어 풀기** (선택 아닌 필수)
   - `D1` → `행사 컨셉`, `D2` → `팀 개수`, `D4` → `입장료` (결정 안건 번호는 의미로)
   - `§3`, `§3-1` → `지침의 게임 양식` / `지침의 성별 항목 안내` (문서 절 참조는 풀어서)
   - `종속` → 의미가 중복되면 생략, 아니면 의미 풀기
2. **내부 전문용어 → 풀어쓰기** (외부인/신규 담당자가 모를 것만)
   - `보전 한도` → `동아리 예산 보전 한도`
   - `주 템플릿` → `주 기준(25-2)`

**금지되는 변경 (건드리지 않는다):**
- 원본 단어/뉘앙스 삭제 ("최소", "각", "오프라인" 등 보존)
- "더 자연스럽게"/"더 짧게" 같은 임의 개선
- 문장 구조 재작성 (어순 바꾸기, 동사형 변환 등)
- 작년 실적/참고를 올해 결정으로 착각 (탑앤탑, 단가 등은 source로)

### 규칙 B — 팀 내 준말은 유지

다음은 기획팀원에게 익숙하므로 그대로 둔다:
- 학기: `25-2`, `26-1`, `25-1`
- 조직: `하클` (하이클럽), `브룸` (동아리 방)
- 캠퍼스: `율전`, `명륜`
- 고유명사: `SG MAPLE`, `Extra Registration` (원문 유지)
- 업체명: `롯데리아`, `탑앤탑`, `게임연구소`

### 규칙 C — 작년 참고/교훈 분리

괄호 안의 작년 참고 패턴을 content에서 제거하고 source 필드로 이동:
- `(25-2: ...)`, `(26-1: ...)`, `(작년: ...)` 패턴 감지
- 작년 실적 수치(탑앤탑 단가, 버스 좌석 수 등)도 source로
- content는 "할 일"만 남김

**예시:**
- content `율전 브룸에 물품 미리 비치`, source `26-1은 명륜 브룸이 없어 당일 혼란`
- content `명륜 버스 탑승자 명단 작성 (2대 분할)`, source `25-2 버스 80석 기준`

### 규칙 D — 고유명사/실적은 건드리지 않기

- `SG MAPLE`은 고유명사 → 절대 바꾸지 않음 (괄호 설명만 다듬기)
- 작년 단가/업체/수량은 **확정이 아니라 참고** → content에 단정적으로 쓰지 않음, source로

## 3. 작업 방식: 3단계 파이프라인

### 3-1. 1차 변환 (최소 수술)

94개 항목 각각에 규칙 A-D를 적용해 변환표 생성.

**출력 형태 (각 항목):**
```
원본: [현재 content]
→ content: [다듬은 content]
→ source: [이동된 source, 있을 경우]
변경 이유: [기호 풀기 / 작년 참고 분리 / 변경 없음]
```

### 3-2. 검증 단계 (자동 체크)

1차 변환 후 원본과 대조해 자동 체크:
- **정보 손실 검사**: 원본의 핵심 명사/숫자가 변환에서 빠지지 않았는지
- **고유명사 보존 검사**: SG MAPLE, 업체명 등이 훼손되지 않았는지
- **content-source 중복 검사**: 작년 참고가 content에 잔류하지 않는지
- **빈 content 검사**: content가 비거나 의미 없는 조각이 되지 않았는지

검증에서 걸린 항목은 플래그 표시 → 수동 재검토.

### 3-3. 사용자 검토 → DB 반영

- 변환표를 사용자에게 제시 (팀별로 그룹핑)
- 승인받은 후 DB에 일괄 UPDATE (새 마이그레이션 0009)

---

## 4. DB 반영 방식

새 마이그레이션 `0009_refine_checklist_content.sql`:

```sql
BEGIN;

-- 94개 항목의 content + source를 일괄 UPDATE
-- 각 UPDATE는 id로 식별, content와 source를 새 값으로
UPDATE public.checklist_items SET content = '...', source = '...' WHERE id = '...';
-- ... (94회)

COMMIT;
```

**주의사항:**
- 마이그레이션 0008에서 milestone_id 매핑을 했으므로, 0009는 content와 source만 건드린다 (milestone_id, team_id, completed 등은 그대로)
- 기존 source 값이 있는 항목은 덮어쓰기 전에 기존 값과 병합 고려 (대부분 NULL이거나 이미 작년 참고)

## 5. 영향받는 파일

### 신규
- `supabase/migrations/0009_refine_checklist_content.sql` — content/source 일괄 UPDATE

### 참조용 (수정 안 함)
- `supabase/migrations/0005_seed_data.sql` — 원본 content 값의 출처 (참조용, 수정 안 함)

- source 필드는 이미 '출처'로 표시되고 있음

## 6. 리스크 & 고려사항

1. **미묘한 판단**: 일부 항목은 "팀 줄임말"인지 "외부 전문용어"인지 경계가 모호 (예: "브룸"은 팀원은 알지만 신규 담당자는 모를 수 있음). 1차 변환에서는 보수적으로 유지하고, 사용자 검토에서 조정.
2. **source 필드 기존값**: 일부 항목은 이미 source에 값이 있음 (5개). 작년 참고를 이동할 때 기존 source와 충돌하지 않게 병합.
3. **사용자 검토 부하**: 94개 항목을 사용자가 일일이 검토하기엔 부담. 팀별로 그룹핑해서 보여주고, 변경이 있는 항목만 강조 표시로 검토 효율화.
4. **되돌리기**: 마이그레이션 0009 적용 후 원복이 필요하면 0005의 원본 content로 복구 가능 (원본은 시드에 보존됨).
