# 설계: 마일스톤 완료 자동동기화 — DB 트리거 이관 (Phase 1)

**날짜**: 2026-08-12
**상위 회고**: `docs/lessons/2026-08-12-대시보드-살리기-회고.md` (액션: "마일스톤 동기화를 DB 트리거로 이관")
**범위**: Phase 1 — DB 트리거 도입 + 클라이언트 동기화 코드 제거.
**Phase 2 (별도 spec)**: 마일스톤 자동완료 optimistic UI.
**구현 의존성**: PR #4(`fix/회고-액션아이템`) 먼저 머지 — `lib/milestone-sync.ts` 로깅 변경과 `0011` 마이그레이션이 기반이므로. 이 spec 문서 자체는 의존 없음.

## 1. 배경 / 문제

마일스톤 `completed` 자동 판정을 현재 **클라이언트**가 담당한다:

- `lib/milestone-sync.ts`의 `syncMilestoneCompletion()` — 체크리스트 변경 후 **전체** checklist_items + milestones를 재조회해 순수 함수(`milestone-completion.ts`)로 완료/롤백 대상을 계산하고 UPDATE.
- `lib/mutations/checklist.ts`의 **3곳**(toggle/add/delete)에서 각각 `void syncMilestoneCompletion().then(() => router.refresh())` 호출.

문제점(회고가 지적):
1. **쓰기 경로마다 수동 호출** — 한 경로라도 빠지면 동기화가 끊긴다. 실제로 trash-view 복원이 같은 `checklist_items` 테이블을 UPDATE하면서 알림/동기화를 빠뜨렸던 사례가 있었음(체크리스트 동기화 회고 1-5).
2. **중복 호출** — 3 mutation에 동일한 호출이 반복.
3. **O(전체) 재계산** — 매번 마일스톤×체크리스트 전체 순회. 변경 1건에도 전체를 다시 읽는다.
4. **책임 소재 오류** — "두 엔티티의 개념적 연결"이라는 DB 불변조건을 앱 계층이 떠안고 있어, DB를 직접 건드리는 경로(SQL 에디터, 다른 클라이언트, 마이그레이션)는 동기화를 우회한다.

## 2. 목표 / 비목표

**목표**
- 마일스톤 자동완료 판정을 **DB 트리거**로 이관 → 모든 쓰기 경로를 트랜잭션 단위로 자동 커버.
- 클라이언트 동기화 코드(`milestone-sync.ts`) 제거 → 중복·누락 클래스 버그 원천 해소.
- **동작 변경 없음** — 기존 클라이언트 의미론(순수 마일스톤 건드리지 않음, 롤백 규칙 등)을 DB가 동일하게 재현. 책임만 이관.

**비목표 (Phase 1에서 안 함)**
- optimistic UI (Phase 2).
- 클라이언트 진행률 계산 통합(별개 주제).
- 기존 RLS/audit 정책 변경.

## 3. 아키텍처

**단일 진실 원천을 클라이언트 → DB로 이관.**

```
[체크 토글 mutation]
   └─ UPDATE checklist_items.completed         (트랜잭션 시작)
        └─ AFTER ROW 트리거 발화 (같은 트랜잭션)
             └─ 영향받은 마일스톤만 카운트 재계산
                  └─ UPDATE milestones.completed  (같은 트랜잭션 커밋)
   └─ onSuccess: router.refresh()              ← 갱신된 마일스톤을 클라이언트로 pull
```

- 트리거가 checklist UPDATE와 **같은 트랜잭션**에서 마일스톤을 갱신 → 추가 왕복 없이 원자적. `router.refresh()` 시점엔 이미 서버 데이터가 일관됨(레이스 없음).
- `milestone-sync.ts`는 **삭제**.
- `milestone-completion.ts`(순수 함수) + 단위 테스트 13개는 **유지** — Phase 2 optimistic UI가 동일 판정 로직을 재사용.

## 4. 트리거 로직

**DB 내 단일 진실을 위해 재계산 로직을 헬퍼 함수 하나에 두고, 트리거·백필·디버그가 모두 호출.**

### 4-1. 헬퍼 `public.recompute_milestone(p_id uuid)`
주어진 마일스톤 1개의 `completed`를 현재 체크리스트 상태 기준으로 재계산:
```
total = count(checklist_items where milestone_id = p_id and deleted_at is null)
done  = count(위 조건 + completed = true)
cur   = milestones.completed (현재값)

if total = 0:
    skip                                   -- 순수 마일스톤(자식 없음) = 사용자 관리
elif done = total:
    if cur is not true: UPDATE milestones set completed = true
else:
    if cur is true:     UPDATE milestones set completed = false   -- 롤백
```
- 멱등: 상태가 실제로 바뀔 때만 UPDATE(cur vs desired 비교).
- `language plpgsql security definer set search_path = public, pg_temp` — 호출자 RLS와 무관하게 DB가 자체 불변조건 유지(표준 패턴). `search_path` 고정은 인젝션 방지.

### 4-2. 트리거 함수 `public.sync_milestone_completion()`
`AFTER INSERT/UPDATE/DELETE FOR EACH ROW`에서 영향받은 마일스톤을 추출해 `recompute_milestone` 호출(중복 제거):
```
INSERT → NEW.milestone_id
UPDATE → OLD.milestone_id, NEW.milestone_id  (둘 다; milestone_id 이동 시 양쪽 재계산)
DELETE → OLD.milestone_id
(각각 null이면 skip)
return coalesce(NEW, OLD)
```

### 4-3. 트리거 부착
```sql
create trigger trg_sync_milestone_completion
  after insert or update or delete on public.checklist_items
  for each row execute function public.sync_milestone_completion();
```

## 5. 엣지케이스 (기존 클라이언트 의미론과의 정합성)

| 상황 | 트리거 동작 | 기존 일치 |
|------|------------|-----------|
| 마지막 항목 체크 → 전부 완료 | `completed = true` | ✅ |
| 완료 항목 하나 해제 | 롤백 `completed = false` | ✅ |
| 미완료 항목 신규 추가(완료된 마일스톤 밑) | 롤백 (불완전 자식 생김) | ✅ |
| 항목 soft-delete(`deleted_at` UPDATE) | 카운트에서 제외 → 재계산 | ✅ |
| 마지막 미완료 항목 soft-delete | 자동 완료 | ✅ |
| `milestone_id` 이동(UPDATE) | OLD+NEW 양쪽 재계산 | ✅ |
| hard DELETE | OLD.milestone_id 재계산 (앱은 soft-delete만 쓰므로 희귀) | ✅ |
| 순수 마일스톤(자식 0) | 건드리지 않음 — 사용자 직접 토글(`useToggleMilestone`) | ✅ |
| **수동 미완료**(자식 전부 완료인 마일스톤을 사용자가 uncheck) | 트리거 미발화(checklist 기준) → 다음 checklist 변경 시까지 미완료 유지 | ✅ (기존 한계 보존, 아래 노트) |
| 재귀 | milestones UPDATE → audit 트리거(0003)만 → checklist 변화 없음 → 종단 | ✅ 안전 |

**보존된 한계(문서화)**: 마일스톤을 수동으로 미완료해도 자식이 전부 완료면, 다음 checklist 변경이 있을 때까지 미완료로 남는다. 이는 기존 클라이언트 동작(`findMilestonesToComplete`가 checklist 변경 시에만 실행)과 동일하며, Phase 1은 동작 변경을 하지 않는다.

## 6. 마이그레이션 `0012_milestone_completion_trigger.sql`

구조(순서대로):
1. `recompute_milestone(p_id uuid)` 함수 생성 (security definer)
2. `sync_milestone_completion()` 트리거 함수 생성
3. 트리거 부착 (`drop trigger if exists` 먼저 — 재실행 안전)
4. **1회성 백필**: `select recompute_milestone(id) from milestones where deleted_at is null;`
   - 과거 클라이언트 sync가 놓친 부정합(trash-view류)을 현재 checklist 상태 기준으로 보정 → 트리거가 깨끗한 기저에서 시작.
   - 백필은 milestones를 직접 UPDATE → checklist 트리거가 발화하지 않음(안전).

`BEGIN; ... COMMIT;`로 감싸 마이그레이션 단위 원자성 확보(기존 마이그레이션 규칙 준수).

## 7. 배포 순서 (갭 방지 — 중요)

```
1) 0012 마이그레이션 적용 (트리거 활성 + 백필)
   → 구클라이언트 sync도 여전히 살아있음 → 양쪽 실행(멱등, 동일 결과) ✅
2) 검증 SQL + UI 로 트리거 동작 확인
3) 클라이언트 sync 제거 코드 배포 (milestone-sync.ts 삭제 + mutation 3호출 제거)
```
- **역순 금지**: 클라이언트 제거를 먼저하면 어느 쪽도 안 도는 갭 창이 생겨 마일스톤이 갱신되지 않는다.
- 1~3단계 사이의 **의도적 겹침 창**이 안전망. 어느 시점에도 동기화가 끊기지 않는다.
- **롤백**: 트리거에 문제가 있으면 `drop trigger trg_sync_milestone_completion` → 구클라이언트 코드(아직 살아있음)가 책임을 재인수. 클라이언트 제거(3단계) 배포 전까지만 양쪽이 공존하므로 롤백이 단방향으로 안전.

## 8. 검증 (회고 "수동검증 = 인간 병목" 교훈 반영)

`scripts/verify-milestone-trigger.sql` — 트랜잭션 + `ROLLBACK`으로 **파괴 없이** 5개 시나리오를 도는 재실행 가능 SQL:
1. 자식 전부 완료 → `completed = true`
2. 하나 해제 → 롤백 `false`
3. 미완료 항목 추가(완료된 마일스톤) → 롤백
4. 마지막 미완료 항목 soft-delete → 자동 완료
5. 순수 마일스톤(자식 없음) → `completed` 변화 없음

- dev Supabase(SQL 에디터 또는 psql)에서 실행. 결과는 사람이 눈으로 확인(이 부분만 인간 게이트 — 자동 DB 통합 테스트 인프라가 없으므로).
- 기존 `milestone-completion.test.ts`(순수 함수 13개)는 그대로 green → **판정 로직은 TS·DB에 동일 규칙으로 이원화**.

## 10. 유지보수 노트

- **이원화된 판정 로직**: 같은 규칙이 (a) TS `milestone-completion.ts` (Phase 2 optimistic UI용)와 (b) SQL `recompute_milestone` (DB 불변조건용)에 존재. 규칙이 바뀌면 **양쪽을 같이 갱신**해야 한다. Phase 1 구현/리뷰 시 두 구현이 동일 규칙을 인코딩했는지 대조.
- 백필은 한 번 실행되면 이후 재실행 불필요(트리거가 유지). 마이그레이션은 불변.
