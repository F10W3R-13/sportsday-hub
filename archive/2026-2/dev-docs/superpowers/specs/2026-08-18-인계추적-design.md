# 설계: 인계 추적 (handoffs) — 팀 간 파일 공유 가시화 2단계

**날짜**: 2026-08-18
**범위**: `handoffs` 테이블 + 대시보드 '인계 현황' 위젯 + `/handoffs` 관리 페이지 + 초기 시드 5건.
**확정 사항**: 독립 handoffs 엔티티(1단계 브레인스토밍 합의) · 받는 쪽 5팀+외부 조직 허용 · 대시보드 위젯 + 전용 페이지 · 파일 연동은 자동 힌트만(완료 수동) · 자체 `due_date` + 상태 2단계(접근법 A, 2026-08-18 승인).

---

## 1. 배경 / 문제

- 인계 하나가 체크리스트에서 **주는 팀 항목과 받는 팀 항목에 나뉘어** 존재한다 (예: 컨텐츠팀 "필요 물품 리스트 → 예산팀 인계" ↔ 예산팀 "게임 물품 리스트 수령 (컨텐츠팀 8/16 완성 후)"). 어느 한쪽을 완료 체크해도 반대쪽 상태와 어긋나고, 전체 인계가 몇 건이나 되는지 한눈에 볼 곳이 없다.
- 받는 쪽이 팀이 아닌 경우도 있다 — 교환팀 "홍보부 인계 (8/18, 8/30)"처럼 외부 조직 대상 인계는 팀 페이지 어디에도 속하지 않는다.
- 1단계 파일 피드가 "무엇이 도착했나"를 보여주므로, "무엇을 언제까지 누가 누구에게 줘야 하나"를 나란히 보여주면 기한 대비 준비 상태가 드러난다.

## 2. 목표 / 비목표

**목표**
- 인계를 한 건의 계약으로 등록·추적: 주는 팀 → 받는 쪽(내부 팀 or 외부 조직), 무엇을, 언제까지, 완료 여부.
- 대시보드 '인계 현황' 위젯(미완료 urgency순 6건, 지연/임박 배지) — 기한 경과가 즉시 보임.
- 인계 행에 **주는 팀의 최근 드라이브 파일 자동 힌트** — "기한 지났는데 아직 파일이 안 보인다" 판별.
- `/handoffs` 페이지에서 등록·완료 토글·편집·삭제(소프트).
- 근거 체크리스트 항목 링크 → 행 클릭 시 팀 체크리스트 딥링크(`?tab=checklist&focus=`, 1단계 인프라 재사용).

**비목표 (안 함)**
- 완료 자동 추정(파일명 매칭 등) — 완료는 사람이 표시.
- 알림(Slack 등), 인계 통계·히스토리 뷰.
- 마일스톤 조인 기한 — 인계 기한은 마일스톤과 1:1이 아니므로 자체 `due_date`.
- 3단계 상태(진행중) — 이 규모에서 구분 애매, 2단계(대기/완료)로 충분.
- `/api/drive/sync` 인가 강화 — 별도 논의 (1단계 최종 리뷰 권장 과제).

## 4. 데이터 모델 — 마이그레이션 `0014_handoffs.sql`

```sql
BEGIN;

create table public.handoffs (
  id uuid primary key default gen_random_uuid(),
  from_team_id text not null references public.teams(id),
  to_team_id text references public.teams(id),
  to_external text,
  title text not null,
  due_date date,
  completed boolean not null default false,
  checklist_item_id uuid references public.checklist_items(id) on delete set null,
  sort_order int not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  deleted_at timestamptz,
  constraint handoffs_to_exactly_one check (
    (to_team_id is not null and to_external is null) or
    (to_team_id is null and to_external is not null)
  )
);

alter table public.handoffs enable row level security;
create policy "handoffs_open_read"  on public.handoffs for select using (true);
create policy "handoffs_open_write" on public.handoffs for insert with check (true);
create policy "handoffs_open_edit"  on public.handoffs for update using (true);
create policy "handoffs_open_del"   on public.handoffs for delete using (true);

-- 감사 트리거 부착 (0003 audit_capture 패턴 그대로 재사용)
-- + 초기 시드 5건 (아래)

COMMIT;
```

**초기 시드** (전부 `completed = false` — 사용자가 UI에서 완료 체크):

| from | to | title | due | checklist 링크 |
|---|---|---|---|---|
| content | budget | 게임별 필요 인원·물품 리스트 | 2026-08-16 | 728a5f1a (필요 물품 리스트 → 예산팀 인계) |
| content | exchange | 컨텐츠 안내 (카드뉴스용) | NULL | 8cc9ec56 (컨텐츠 안내 → 교환담당팀 인계) |
| exchange | 외부: 홍보부 | 카드뉴스 홍보부 인계물 (1차) | 2026-08-18 | 40f95907 (홍보부 인계) |
| exchange | 외부: 홍보부 | 카드뉴스 홍보부 인계물 (2차) | 2026-08-30 | 40f95907 (홍보부 인계) |
| exchange | timeline | 버스 탑승 명단 | NULL | 902c4cc4 (교환담당팀에서 전달) |

※ 체크리스트 ID는 `0005_seed_data.sql` 기준. 1차(8/16)는 즉시 지연 배지로 표시 — 의도된 첫 화면.

**마이그레이션 적용**: 이번에도 사용자가 수동 적용 (DDL + 시드). 적용 전 배포하면 `getHandoffs()` 에러가 §7 폴백으로 흡수돼 위젯은 빈 상태로 동작하므로 치명적이지는 않지만, 시드 없이 출시되는 것을 막기 위해 **적용 후 배포를 원칙**으로 한다.

## 5. 데이터 레이어

**`lib/types/models.ts`**
```ts
export const handoffSchema = z.object({
  id: z.string().uuid(),
  from_team_id: z.enum(TEAM_IDS),
  to_team_id: z.enum(TEAM_IDS).nullable(),
  to_external: z.string().nullable(),
  title: z.string(),
  due_date: z.string().nullable(),
  completed: z.boolean(),
  checklist_item_id: z.string().uuid().nullable(),
  sort_order: z.number(),
  created_at: z.string().optional(),
  updated_at: z.string().optional(),
  deleted_at: z.string().nullable().optional(),
})
export type Handoff = z.infer<typeof handoffSchema>
export type HandoffItem = Handoff & {
  from_team: { id: TeamId; name: string; color: string }
  to_team: { id: TeamId; name: string; color: string } | null
  checklist_content: string | null   // 링크된 항목 내용 (표시 라벨용)
  checklist_team_id: TeamId | null   // 링크된 항목의 소속 팀 — 딥링크 대상
}
```

**`lib/handoff.ts` (순수함수 — 전부 테스트 대상)**
- `handoffUrgency(dueDate: string | null, completed: boolean, today = new Date()): 'overdue' | 'due_soon' | 'scheduled' | 'no_due'` — completed면 항상 `scheduled` 취급(정렬에서 완료 후위가 관리). 지연 = due < 오늘 자정. 임박 = 오늘~3일 이내(`milestones-urgency`의 오늘 자정 기준 패턴 준용).
- `sortHandoffs(items: HandoffItem[], today?): HandoffItem[]` — 미완료 우선, 그 안에서 urgency순(overdue→due_soon→scheduled→no_due)·같은 티어는 due 오름차순, 완료는 뒤로(updated_at 내림차순).
- `handoffDirectionLabel(h: HandoffItem): string` — `"컨텐츠팀 → 예산팀"` / `"교환담당팀 → 홍보부"`. 팀명은 `HandoffItem.from_team`/`to_team`에서 직접 도출, 외부는 `to_external` (외부 태그는 UI에서 별도).
- `validateHandoffTarget(toTeamId: string | null, toExternal: string | null): string | null` — 정확히 하나만, 외부명 공백 제거 후 비었으면 오류 메시지 반환(null = 유효).

**`lib/queries/handoffs.ts`**
- `getHandoffs(): Promise<HandoffItem[]>` — `handoffs` (`deleted_at is null`) + `teams` + `checklist_items`(id·content·team_id·deleted_at만) 3개 조회를 앱 레이어에서 병합. 팀 메타 폴백은 1단계 `FALLBACK_TEAM` 패턴 준용(회색 '알 수 없음').

**`lib/mutations/handoffs.ts`** (기존 `lib/mutations/*` 패턴)
- `createHandoff / updateHandoff / setHandoffCompleted / softDeleteHandoff` — 전부 `ensureContext()` 후 anon 클라이언트로 쓰기. 감사는 DB 트리거가 담당.

## 6. 컴포넌트

**`components/handoffs/handoffs-widget.tsx` (서버)**
- 대시보드 **파일 피드 위젯 아래** 배치. `sortHandoffs` 상위 6건.

- `checklist_item_id` 있으면 행 전체를 체크리스트 딥링크로(`buildChecklistFocusUrl` 재사용 — 해당 팀 `?tab=checklist&focus=`).
- 빈 상태: "등록된 인계가 없습니다" + `/handoffs` 링크.

**`app/handoffs/page.tsx` + `components/handoffs/handoffs-client.tsx`**
- 서버: `getHandoffs()`·`getTeams()`·`getRecentDriveFiles(50)` 병렬 fetch.
- 목록: `sortHandoffs` 전체, 완료 행은 흐리게. 받는 쪽 필터 칩(전체+5팀+외부) — `?to=` URL 연동(1단계 `?team=` 패턴).
- **등록·편집 다이얼로그**(기존 편집 모달 패턴): from select · to select or '외부' 토글(텍스트 입력) · title · date input(due, 공백 허용) · 관련 체크리스트 select(선택, 항목 내용 표시). 클라이언트 검증: `validateHandoffTarget`, from ≠ to.
- 행 액션: 완료 토글(즉시 반영·optimistic), 편집, 소프트삭제(확인 한 번).
- 힌트: /handoffs에서도 주는 팀 최신 파일 표시(위젯과 동일 로직, 공용 소형 컴포넌트로).

**대시보드 `app/page.tsx` 수정**
- `getRecentDriveFiles(8)` → `getRecentDriveFiles(50)`로 상향, 파일 위젯은 `.slice(0, 8)`, 인계 위젯은 팀별 최신 파일 맵 사용. `getHandoffs()` 추가.

## 7. 오류 처리

| 상황 | 동작 |
|---|---|
| handoffs 테이블 부재(마이그레이션 미적용 배포) | `getHandoffs()` 쿼리 에러를 `.catch(() => [])`로 흡수 — 위젯은 빈 상태, 대시보드는 죽지 않음 (1단계 `.catch` 폴백 패턴) |
| 팀 메타 매핑 불능 | 회색 폴백 배지('알 수 없음') |
| due_date null | '—' 표시, 정렬은 미완료 중 가장 뒤 |
| 체크리스트 링크 대상 소프트삭제/삭제 | `checklist_content` 조회에서 제외 → 행은 유지, 딥링크만 숨김 |
| from = to | 폼에서 차단(전송 불가), DB는 허용(제약 최소화) |
| 닉네임 미설정 | 기존 패턴대로 '익명'으로 감사 기록 |

## 8. 테스트 (vitest, node 환경 순수함수)

- `handoffUrgency`: 경계 — 어제 due(overdue) / 오늘 due(due_soon) / 3일 후(due_soon) / 4일 후(scheduled) / null(no_due) / completed면 due 무시.
- `sortHandoffs`: 미완료 우선·티어 내 due 오름차순·완료 후위·no_due 후위.
- `handoffDirectionLabel`: 내부→내부, 내부→외부, 매핑 불능 폴백.
- `validateHandoffTarget`: 팀만/외부만 OK, 둘 다·둘 다 없음·외부 공백 오류.
- `getHandoffs` mock: 3원 조인(팀·체크리스트), 폴백, deleted_at 제외.

## 9. 배포 순서

1. 운영 Supabase에 `0014_handoffs.sql` 적용 (DDL + RLS + 트리거 + 시드)
2. 머지·배포 → 대시보드 위젯·/handoffs 확인
3. 시드된 1차 인계(8/16 지연)가 지연 배지로 보이는지 확인 — 완료됐다면 완료 토글

## 10. 결정 기록

- 접근법 A(자체 due_date + 2단계 상태) 확정 — 2026-08-18. 기각: B(마일스톤 조인·3단계 상태)는 인계 전용 기한 표현 불가·규모 대비 과함.
- 받는 쪽 외부 조직 허용 — "홍보부 인계" 실제 사례 때문. 상호배타 CHECK 제약으로 데이터 정합 유지.
- 파일 연동은 자동 힌트만 — 파일명 매칭 오탐·선택 UI 복잡도로 완료 시 파일 지정은 기각(필요시 확장).
- 감사는 기존 열린 편집 철학 준용 — 인가 강화는 별도 과제.
