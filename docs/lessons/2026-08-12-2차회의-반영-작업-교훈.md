# 2차 회의록 웹앱 반영 작업 — 회고/교훈

> **작업일**: 2026-08-12
> **작업**: 2차 회의록(2026-08-09 22:00)의 결정·진행 상황을 웹앱 DB(마일스톤·결정·체크리스트)에 반영
> **성과**: 마일스톤 3건 완료, 결정 3건 갱신(D5/D6/D7), 체크리스트 5건 완료 처리
> **문서 성격**: 이 작업에서 **직접 겪은** 구체적 문제와 병목의 기록. 일반론이 아님.

## TL;DR — 핵심 2가지

1. **마이그레이션 드리프트**: 마이그레이션 파일이 소스 오브 트루스가 아니었다. 파일은 존재했지만 실제 DB는 불일치 상태.
2. **"전부 완료로 반영"의 정직성 장력**: 진행 추적 앱에서 "전부 완료"라는 말을 글자 그대로 따르면 거짓 상태를 만든다.

## 1. 마이그레이션 드리프트 (가장 심각한 백엔드 문제)

### 현상
`supabase/migrations/0010_reflect_2nd_meeting.sql` 파일이 **이미 존재**했는데, 정작 프로덕션 DB는 그 마이그레이션과 **불일치**하는 상태였다.

| 항목 | 마이그레이션 파일 기대값 | 실제 DB |
|---|---|---|
| `6d445bf1` (컨텐츠 8/9) | completed=true | completed=true ✓ |
| `05e80dca` (2차 회의) | completed=true | **completed=false ✗** |
| `11e1561a` (예산 8/9) | completed=true | **completed=false ✗** |
| D5 status | confirmed | confirmed (그러나 current_value는 구값 그대로) |

→ 마이그레이션의 **절반만** 적용된 상태. D5는 status만 바뀌고 본문은 갱신 안 됨.

### 교훈
- 마이그레이션 파일이 "영구 기록"을 자처하지만, 누군가(UI 편집 또는 수동 쿼리)가 DB를 직접 건드리면 둘은 곧바로 갈라선다. 파일은 소스 오브 트루스가 아니라 **희망 사항**에 가깝다.
- 작업 전에 "이 마이그레이션이 DB에 실제로 적용되었는가?"를 SELECT로 먼저 검증해야 한다. 이번엔 다행히 발견했다.

### 개선 방향
- 마이그레이션 적용 이력 추적(supabase migration 목록 vs DB)을 작업 전 표준 체크로.
- 데이터를 건드리는 UI 편집 경로가 있으면, 마이그레이션과 충돌하는지 감지하는 장치 필요.

## 2. Windows Git Bash + curl 유니코드 인코딩 파손

### 현상
decision UPDATE를 아래처럼 보냈더니 **HTTP 400 (PGRST102 "Empty or invalid json")** 반환:
```bash
curl -d '{"current_value":"한식 도시락·돈치스팸 도시락..."}'
```
`status`만 보내면 204로 성공 → 본문 인코딩이 원인.

### 원인
Git Bash가 `-d`의 JSON 문자열 안 한국어/특수문자(`·`, `→`) 바이트를 **전송 전에 깨뜨린다**. `echo`로 찍은 한국어 라벨도 모지바깟로 출력되었다 (데이터 자체는 정상).

### 해결
JSON을 임시 파일로 쓰고 `--data-binary @file`로 전송:
```bash
printf '%s' '{"current_value":"..."}' > /tmp/d5.json
curl --data-binary @/tmp/d5.json
```

### 교훈
- Windows + Git Bash에서 한국어가 핵심인 앱을 다룰 때, 셸 파이프라인 자체가 인코딩을 훼손한다.
- 본문 페이로드는 **파일 기반**(`--data-binary @file`)으로만 보낸다.
- `echo` 출력을 곧이곧대로 믿으면 안 된다. 실패 3회를 이 원인 진단에 소모했다.

## 3. 마일스톤 자동완료 매핑의 빈틈 (데이터 모델링 이슈)

### 현상
`lib/milestone-completion.ts`는 "하위 체크리스트가 전부 완료되면 마일스톤 자동완료" 로직이다. 그런데 `0008_checklist_milestone_integration.sql` 매핑을 보면:

- 8/9 날짜 마일스톤이 **3개**(2차 회의 / 컨텐츠 방향 / 예산 방향)
- 체크리스트는 전부 `05e80dca`(2차 회의) **하나에만** 매핑
- 나머지 둘(`6d445bf1`, `11e1561a`)은 **하위 항목 0개** → 자동완료 로직이 동작하지 않는 "순수 마일스톤"

→ 같은 회의 산물인데 세 마일스톤의 매핑 정책이 달라서, 두 개는 영원히 자동완료 혜택을 못 받는다. 시드 재생성 시 다시 빈 상태로 돌아갈 위험.

### 교훈
- "마일스톤 = 체크리스트 그룹" 추상이 매력적이지만, 같은 날짜/같은 회의의 산물이 여러 마일스톤으로 쪼개지면 매핑이 불완전해지기 쉽다.
- 매핑 마이그레이션 작성 시 일관성 검사("모든 deliverable 마일스톤이 ≥1 하위 항목을 갖는가?")가 있어야 한다.

### 개선 방향
- 시드/매핑 마이그레이션에 대한 테스트: `findMilestonesToComplete`가 빈 하위를 가진 deliverable 마일스톤을 발견하면 경고.
- 또는 같은 회의의 산물 마일스톤은 하나로 합치거나, 하위를 명시적으로 분배.

## 4. "전부 완료로 반영" 요청의 모호성 (사용자 병목)

### 현상
요청 문장: "반영 가능한 모든 곳에 전부 다 '완료' 또는 **뭔가 아무튼 다 되었다는 상태**로 반영"

두 가지로 해석된다:
1. 회의록 근거 있는 것만 정직하게 완료 처리 ← 선택됨
2. 회의에서 언급된 것 전부(심지어 8/16, 9/3 미래 일정까지)를 "됨"으로

만약 2번으로 임의 해석했으면, **아직 시작도 안 한 9/3 팀 배정을 "완료"로 표시**하는 결과가 나왔을 것이다. 멈춰서 AskUserQuestion으로 물었고, 다행히 1번을 선택받았다.

### 교훈
- 진행 추적 앱에서 "전부 완료"라는 말은 위험하다. 글자 그대로 따르면 거짓 상태를 만든다.
- "뭔가 아무튼 다 되었다"는 뉘앙스가 특히 위험. 항목별 판단이 필요했다.
  - 예: D7 점수배분은 회의록에 "잠정"으로만 되어 있어 `discussing`으로 두고 `confirmed`로 올리지 않음 → 정직한 판단.
- **사용자의 강한 표현이라도 상태를 과장하지 않는 선을 지킨다.** 추적 앱의 완료 상태는 신뢰의 근간이다.

### 개선 방향
- "완료 처리" 작업 요청이 오면, 항상 "어디까지 완료로 볼 것인가" 범위를 먼저 확정하는 단계를 둔다.

## 5. DB 쓰기 ≠ 사용자 화면 (검증 루프)

### 현상
service role key로 DB UPDATE 후, "배포환경에서도 보이는가?" 질문에 세 단계 검증을 실행:
1. **service role** 재조회 — 데이터 들어갔나
2. **anon key** 조회 — RLS 통과하는가 (실제 방문자와 동일 권한)
3. **프로덕션 URL HTML 페치** — SSR 결과에 실제 렌더링되는가

### 핵심
- 2번이 핵심. service role은 RLS를 우회하므로, 내가 쓴 게 일반 사용자에게 안 보일 수도 있었다 (다행히 `0002_rls_policies.sql`이 "전체 오픈"이라 문제없었음).
- 3번까지 가서야 "DB 변경 = 사용자 경험" 마지막 한 끝이 닫혔다. 프로덕션 HTML에 D5/D6/D7 새 값이 그대로 박혀 있음을 확인.

### 남은 이슈
- 대시보드 통계 카드(확정 0 / 논의중 2 / 보류 1)가 SSR 시점 캐시일 가능성. 브라우저 재방문 시 갱신될 것으로 보이나, 확인이 필요한 상태로 남겨둠.

### 교훈
- "저장했습니다"와 "사용자가 봅니다"는 다르다. RLS 정책·SSR 캐시·클라이언트 재페치 세 계층이 다 끼어 있다.
- 데이터 작업 후에는 반드시 anon key 조회 + 프로덕션 화면 확인으로 마지막 한 끝를 닫는다.

## 6. service role vs anon key (권한 분리)

### 현상
- **쓰기**: service role key (RLS 우회, 관리자 권한)
- **읽기 검증**: anon key (실제 방문자와 동일 권한, RLS 적용)

### 교훈
- 데이터를 쓸 권한과 읽을 권한을 분리해 생각해야 한다. service role로 썼다고 해서 anon key 사용자가 읽을 수 있다고 가정하면 안 된다.
- 검증은 항상 **가장 낮은 권한**으로 한다.
