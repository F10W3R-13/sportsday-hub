이번 세션의 거의 모든 문제가 이 근원에서 비롯됐다.

## 1. 백엔드/데이터 설계 문제점

### 1.1 마일스톤과 체크리스트의 "개념적 연결 ≠ 기술적 연결" ★가장 뼈아픔

데이터 모델상 `checklist_items.milestone_id`로 둘이 연결되어 있지만, **`completed` 상태는 완전히 독립**이었다.

```
milestones.completed ──(연결 안 됨)── checklist_items.completed
```

- `components/timeline/timeline-list.tsx:252-258`에서 하위 체크리스트가 있으면 마일스톤 체크박스를 비활성화하고 진행률(`2/4`)만 표시한다.
- 하지만 **`2/4 → 4/4`가 되어도 마일스톤 `completed`는 자동으로 `true`가 안 됐다.** 사용자가 체크를 다 해도 마일스톤은 미완료로 남아, 대시보드 위젯에서 사라지지 않는 상태.
- "사용자는 자연스럽게 연결되었다고 가정하지만, DB는 모른다"는 **전형적인 멘탈 모델 불일치**.

**해결:** 옵션 A(`lib/milestone-sync.ts`)로 자동 동기화를 넣었지만, 근본적으로 이건 **DB 트리거**가 담당해야 할 책임을 클라이언트 mutation에 떠넘긴 상태다. mutation 3곳(toggle/add/delete)에 각각 `syncMilestoneCompletion()`을 호출해야 해서 **누락 위험**이 남아있다.

**다음 액션:** DB 트리거(`0011` 마이그레이션)로 이관하면 모든 쓰기 경로를 한 번에 커버.

### 1.2 RLS는 열려있는데 앱이 막는 "보이지 않는 제약"

`supabase/migrations/0002_rls_policies.sql`이 `decisions` 테이블의 INSERT/DELETE를 허용하지만, **mutation 훅/UI가 UPDATE 하나뿐**이라 사용자는 사실상 읽기 편집만 가능했다.

- "DB가 허용한다 = 앱이 된다"가 **아니다**. 앱 계층이 진짜 게이트키퍼.
- 결정 추적표에서 처음 발견 — D1~D7이 시드 고정이라 추가/삭제가 불가했다.

### 1.3 시드 데이터의 신선도 부담

회의가 끝나도 DB는 시드 기준(회의 전)으로 고정. "라이브 데이터"를 시드와 동기화하려면 매번 마이그레이션을 써야 했다(`0010_reflect_2nd_meeting.sql`).

- 시드 기반 프로토타입의 고질적 부담 — **영구 기록(마이그레이션)과 임시 편집(UI)의 경계**가 모호해진다.
- 회의록 반영을 두 방식(마이그레이션 vs 웹 UI 편집)으로 고민한 것도 이 때문.

## 2. 사용자 병목 / UX 문제

### 2.1 "다가오는"이라는 단어의 해석 차이 ★가장 큰 사용자 병목

원래 마일스톤 위젯은 `parseISO(m.date) >= now` 필터로 "오늘 이후"만 표시했다. 결과적으로:

- 🔴 **지연된 마일스톤이 가장 급한데 완전 숨겨짐**
- 오늘 당일 항목이 시간에 따라 잘림 (오후에 보면 오늘 게 사라짐)
- 체크리스트 시급함은 아예 안 보임 (마일스톤만 표시)

**교훈:** 위젯의 필터가 "정보 은닉"으로 작동하면 안 된다. 숨기는 것보다 시급함으로 강조하는(unread → 빨간) 쪽이 낫다. `lib/milestones-urgency.ts`의 overdue/today/upcoming tier가 이 교훈의 산물.

### 2.2 "UI가 안 바뀌었는데 된 건가?" — 동작 변경의 확인 어려움

결정 추적표 동기화를 배포했을 때 사용자가 "UI는 달라진 게 없는데 정상인가?"라고 물었다. 맞다 — **동작(behavior) 변경은 화면에 안 보인다.** SSR HTML은 동일하고, 차이는 상호작용 후에만 나타난다.

**교훈:** 동작 변경을 배포할 때는 **"무엇을 테스트해야 하는지"를 명시적으로 안내**하지 않으면 사용자가 검증할 수 없다. "이걸 클릭하면 X가 일어나야 정상" 형태의 가이드 필수.

### 2.3 N개 제한이라는 정보 은닉

`.slice(0, 5)`로 상위 5개만 표시 — DB엔 29개 마일스톤이 있는데 5개만 보이면 "이게 전부인가?" 오해가 생긴다.

**교훈:** 임계값은 "더 보기" 링크나 카운트("전체 29개 중 5개 표시")로 보완해야 한다.

## 3. 배포/프로세스 교훈

### 3.1 Squash merge + 로컬 머지 충돌 ★가장 고통스러웠던 부분

PR #3이 GitHub에서 **squash-merge**되어 `dd0fe91`이라는 별개 커밋(원본 여러 커밋을 하나로 압축)이 됐다. 로컬에서 feat 브랜치를 main에 머지하려니 **add/add 충돌**이 났다 (같은 내용이 다른 SHA로 존재). `git pull`이 자동으로 복잡한 merge 커밋을 만들어 상황이 악화.

**해결:** 백업 브랜치 생성 → `reset --hard origin/main`으로 정리 → feat 재머지 → 충돌 수동 해결.

**교훈:** squash-merge 워크플로우에서는 **로컬 직접 머지를 피하거나, reset 후 fast-forward로 재정렬**해야 한다.

### 3.2 Vercel 배포 모델 이해

- 피처 브랜치 푸시 = **preview** 자동 배포
- main 머지 = **production** 배포
- "커밋했는데 반영 안 됐다" = **production에는 main 머지가 필요**하다는 걸 깨달음.
- Vercel MCP(`list_deployments`, `get_deployment`)로 배포 상태 직접 확인 가능.

### 3.3 SDD(Subagent-Driven Development) 파이프라인 경험

brainstorming → spec → plan → SDD(subagent per task + task review + final review) 전체 파이프라인을 결정 추적표 동적화에 적용. **task마다 fresh subagent + 독립 리뷰**가 컨텍스트 오염 없는 품질 보증에 효과적이었다. 단, mechanical한 작업(단일 파일, 플랜에 코드까지 있는 경우)엔 저렴한 모델로 충분.

## 4. 내 코드의 한계 (솔직 회고)

### 4.1 `lib/milestone-sync.ts`의 에러 잠식(swallow)

```ts
} catch {
  // 잠식: 체크 토글은 성공했으므로 마일스톤 동기화 실패를 토글 실패로 만들지 않음
}
```

마일스톤 동기화 실패를 조용히 무시한다. 의도된 설계(토글 실패로 만들지 않기 위함)이지만, **실패 시 아무 알림이 없어서 "체크했는데 마일스톤이 안 닫혔다"를 디버깅하기 어렵다.** 최소한 콘솔 경고나 Sentry 정도는 남겼어야 했다.

### 4.2 동기화 지연 가능성

`syncMilestoneCompletion().then(() => router.refresh())`로 순서는 보장했지만, 서버 재조회 1~2초 + 네트워크 지연이면 사용자가 "체크했는데 바로 안 닫혔다"고 느낄 수 있다. **optimistic UI**로 마일스톤 `completed`를 클라이언트에서 먼저 바꿨어야 했다.

### 4.3 옵션 A의 단점을 사용자에게 충분히 못 알림

"체크리스트 다 하면 마일스톤이 닫힌다"는 규칙이 "팀장 승인 대기 중인데 체크만 하면 자동 완료된다" 같은 케이스와 충돌할 수 있다. UI에 안내가 없으면 사용자가 이 규칙을 발견하기 어렵다.

| 마일스톤 자동완료에 **optimistic UI** 추가 | 체크 즉시 마일스톤도 닫힌 것처럼 표시 | High |
