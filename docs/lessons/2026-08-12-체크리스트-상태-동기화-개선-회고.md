# 회고: 체크리스트 상태 동기화 개선

**작성일**: 2026-08-12
**대상 작업**: 체크리스트/마일스톤 체크 상태의 다중 화면·다중 탭 동기화 개선
**관련**: PR #3, `docs/superpowers/specs/2026-08-09-체크리스트-상태-동기화-개선-design.md`
**성격**: 코드/실행에서 **직접 관찰한** 사실에 기반. 추측·일반론이 아님.

---

## 0. 작업 한 줄 요약

체크리스트 상태가 여러 화면·탭에 걸쳐 일관되게 동기화되는지 조사 → 3가지 이슈(진행률 불일치, 낙관적 UI 롤백 누락, 교차 탭 동기화 미흡)를 발견 → 설계→계획→구현(TDD, 6 태스크)→리뷰→fix→PR까지 완료. **데이터는 단일 테이블로 잘 통합되어 있었지만, 표시 계층의 계산·동기화·롤백이 분산되어 있었다.**

---

## 1. 백엔드/아키텍처 문제점

### 1-1. 계산 로직 중복이 정합성 버그의 근원

데이터는 단일 테이블(`checklist_items`)로 잘 통합되어 있었으나, **진행률 "계산"이 3곳에 따로 존재**했다. 같은 데이터를 읽어도 화면마다 공식이 달랐다:
- 대시보드/팀 페이지 → 체크리스트 항목만
- 타임라인 → 체크리스트 + (하위 체크리스트가 없는 독립 마일스톤) 합산

→ **교훈**: SSOT(Single Source of Truth)는 **데이터 계층뿐 아니라 파생 계산 계층에도** 필요. "데이터는 하나인데 계산이 여럿"이면 정합성 버그는 필연적으로 재발한다. 계산을 `computeProgress()` 하나로 모으면 앞으로 기준이 바뀌어도 한 곳만 고치면 된다.

### 1-2. 집계가 DB가 아니라 메모리에서

대시보드/팀 페이지가 DB 집계 쿼리가 아니라 **전체 checklist 배열을 클라이언트에서 N번 필터링**한다 (`checklist.filter(c => c.team_id === team.id)`). 현재 규모에 문제는 없지만, 데이터가 커지면 매 요청마다 전체 로드 + 메모리 순회 비용이 든다.
→ 후속 고려: 데이터 증가 시 SQL 집계 뷰/함수로 이관.

### 1-3. `router.refresh()`는 현재 페이지만 갱신한다

동기화가 "현재 보고 있는 화면"에만 국한되었다. 다른 탭은 옛 값을 표시 (`refetchOnWindowFocus`가 우연히 보완만 했음). 동일 출처 탭 간 전파 채널이 아예 없었다 → `BroadcastChannel`로 메꿈.
→ **교훈**: 상태 동기화는 "사용자가 어느 탭/페이지를 보고 있든 같은 진실을 본다"까지 설계되어야 한다. 현재 페이지 갱신 ≠ 전역 동기화.

### 1-4. 낙관적 UI에 롤백이 없었다

저장 실패 시 toast만 띄우고 **체크박스는 뒤집힌 채로 잔류** → DB와 UI 불일치. 낙관적 UI는 "롤백"과 쌍이 되어야 비로소 안전하다. 코드로 확인한 사실.

### 1-5. 상태 동기화 경로의 "한 구멍" (trash-view)

전체 브랜치 리뷰에서 잡힌 **가장 중요한 결함**. 토글/추가/삭제엔 `notifyTabs`를 붙였지만, **휴지통 복원이 같은 `checklist_items` 테이블을 직접 UPDATE**하면서 알림을 빼먹었다. "이 브랜치가 만든 새 계약(checklist 쓰기는 무조건 notifyTabs)을 위반하는 기존 코드"였다.
→ **교훈**: 동기화는 **송신 → 채널 → 수신 전 경로**를 봐야 하고, 특히 "그 테이블에 쓰는 **모든** 경로"를 색인해야 한다. 하나만 빠져도 끊긴다. 전체 브랜치 리뷰가 아니면 잡기 어려운 유형.

## 2. 환경/도구 병목 (직접 겪은 것)

### 2-1. 한글 경로 + `pnpm` 크래시

`pnpm`이 프로젝트 경로 `26-2 스포츠데이기획`에서 죽어서 **모든 태스크마다 `npm`/`npx` 우회**를 전달해야 했다. 매 작업 dispatch마다 환경 노트를 반복 기입하는 실비(實費) 병목.
→ **해결책**: 경로를 ASCII로 옮기거나, 루트 `package.json`/README에 `npm` 고정을 명시. 팀원 온보딩 시 동일한 장벽.

### 2-2. 정적 분석 게이트가 사전 부채로 막혀있다 (가장 비용이 컸음)

`scripts/verify-scope-ownership.ts` (untracked, 타 작업 진행 중 파일)가 **`tsc`/`next build`를 중단**시킨다. 결과적으로 "플랜 코드는 전부 통과"인데 "빌드 exit 1"이 공존하는 애매 상태. lint도 마찬가지 — `use-mobile.ts`, `lib/types/database.ts`, `scripts/*.cjs` 등 **기존 위반이 산재**해서 노이즈 속에서 신규 위반을 찾아야 했다.
→ **교훈**: 게이트(tsc/lint/build)는 **항상 녹색인 기준선**을 유지해야 새 위반을 신호로 쓸 수 있다. 지금은 노이즈가 너무 많아 "내 코드가 문제인지 기존인지" 매번 분리 검증해야 했다. 이게 이번 세션의 최대 효율 저하 원인.

### 2-3. 컴포넌트 테스트 인프라 부재 → 인간 검증 부담

vitest가 `environment: 'node'`이고 React Testing Library가 없어서 **순수 함수만 단위 테스트** 가능. 낙관적 UI 롤백·크로스탭 동기화 같은 핵심 동작이 자동 테스트 범위 밖 → 전부 "수동 검증 이관"으로 떠넘겨짐.
→ 이게 이번 세션의 가장 큰 **사용자(인간) 병목**: 핵심 동작 검증이 인간에게 쏠린다.

## 3. 프로세스 병목

### 3-1. 설계 게이트가 4번 멈춤

brainstorming 스킬의 HARD-GATE 때문에 (범위 → 진행률 기준 → 계산 위치 + 롤백/동기화 방식 → 실행 방식)까지 4번 사용자 승인이 필요했다. **합의가 필요한 결정에는 유효**했지만, 단순 작업엔 진입 장벽으로 작동. 설계 의도가 명확한 작업은 게이트를 가볍게 두는 판단이 필요.

### 3-2. 수동 검증 시나리오 = 인간 병목

"네트워크 오프라인 토글 후 롤백 확인", "두 탭 열어놓고 크로스탭 확인"은 에이전트가 수행 불가. **이런 런타임 동작 검증이 전부 인간에게 이관**되는데, 정작 그 시나리오 목록만 PR에 적혀 있고 실행은 안 됐다. 머지 전에 인간이 직접 돌려봐야 한다.

## 4. 핵심 교훈 (한 줄들)

1. **SSOT는 데이터뿐 아니라 파생 계산에도.** 로직 중복이 정합성 버그의 근원.
2. **낙관적 UI는 롤백·prop 동기화와 세트.** 하나라도 빠지면 DB-UI 불일치.
3. **동기화는 송신-채널-수신 전 경로 + "그 테이블에 쓰는 모든 경로" 색인.** 한 구멍이 전체를 무력화.
4. **정적 분석 게이트는 항상 녹색 기준선.** 사전 부채로 더러워지면 신호가 묻힌다.
5. **표준 브라우저 API(BroadcastChannel)가 풀스택 의존성(Supabase Realtime)보다 현재 규모에 적합할 수 있다.** 과잉 엔지니어링 회피.

## 5. 한 줄 요약

> **데이터는 하나였지만 계산·동기화·롤백이 분산되어 있었고**, 그 분산이 정합성 버그와 인간 검증 부담으로 이어졌다. 정적 분석 게이트가 사전 부채로 오염된 상태라 "새 코드가 안전한가"를 매번 수동으로 분리해야 했던 게 가장 비용이 컸다.

## 6. 즉각 추천하는 후속 작업

| 우선순위 | 항목 | 비용 | 효과 |
|---|---|---|---|
| **높음** | `scripts/verify-scope-ownership.ts` 처리 (삭제/수정/tsconfig exclude) | ~0 | 빌드 게이트 녹색화, 신호 명확해짐 |
| **높음** | 컴포넌트 테스트 인프라 도입 (RTL + jsdom) | 중 | 낙관적 UI/동기화 핵심 동작 자동화 — 지금이 가장 비용 효율 좋은 시점 (관련 코드 방금 정리돼 테스트 명세 명확) |
| 중 | 기존 lint 위반 정리 (`use-mobile.ts`, `database.ts`, `scripts/*.cjs`) | 중 | 게이트 기준선 녹색화 |
| 중 | "checklist/milestones 쓰는 모든 경로" 문서화 (동기화 계약 명시) | 낮 | trash-view 같은 누락 재발 방지 |
| 낮 | 한글 경로 → ASCII 이동 또는 npm 고정 명시 | 낮 | 팀원 온보딩 장벽 제거 |

후속 2건(게이트 녹색화 + 테스트 인프라)이 처리되면 앞으로의 동기화/상태 작업이 훨씬 안전해진다.
