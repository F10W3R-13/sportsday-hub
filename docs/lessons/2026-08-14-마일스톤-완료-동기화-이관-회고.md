# 회고: 마일스톤 완료 동기화 — DB 트리거 이관 + optimistic UI

**작성일**: 2026-08-14
**대상 작업**: 회고(대시보드 살리기·체크리스트 동기화)의 High 액션 아이템을 파이프라인으로 실행 — Phase 1(DB 트리거 이관), Phase 2(optimistic UI), 그리고 회고 액션 1-3 즉시 조치 + 회고록 정리.
**커밋 범위**: PR #4 · #5 · #6 (main 기준)
**성격**: 코드/DB/배포에서 **직접 관찰한** 사실에 기반.

---

## 0. 핵심 교훈 (한 줄)

> **회고의 액션 아이템을 brainstorm→spec→plan→execute 파이프라인으로 끝까지 밟아 실제로 해결했다 — 회고는 '쓰고 마는' 문서가 아니라 실행 루프의 입력이다. 단, 진실 원천 이관은 '규칙 이원화'라는 새 부채를 낳는다.**

---

## 1. 백엔드/데이터 설계

### 1-1. DB 트리거로 진실 원천 단일화 (성공)
마일스톤 자동완료 판정을 클라이언트(`milestone-sync.ts`) → `0012` DB 트리거(`recompute_milestone`)로 이관. mutation 3곳(toggle/add/delete) 중복 호출 제거 + trash-view 류 "쓰기 경로 누락" 버그 원천 해소(모든 `checklist_items` 쓰기가 같은 트랜잭션에서 마일스톤 갱신). 같은 트랜잭션이라 왕복 하나 감소.

### 1-2. 규칙 이원화 — 새 부채 ★가장 중요한 새 이슈
"완료 판정" 규칙이 **DB(SQL `recompute_milestone`)** 와 **TS(`shouldCompleteMilestone`)** 두 곳에 존재. Phase 2 optimistic은 TS를 재사용해 3곳→2곳으로 줄였지만, SQL↔TS 간 동기화 부담은 남는다. 규칙이 바뀌면 양쪽을 같이 고쳐야 함.
→ **교훈**: 진실 원천 이관은 중복을 줄이면서도 다른 형태의 이원화(DB 언어↔앱 언어)를 낳는다. 완전 단일화는 불가능(서로 다른 런타임)하므로, 규칙 변경 시 양쪽 갱신을 강제하는 체크리스트/테스트가 필요.

### 1-3. 헬퍼 함수로 DB 내 DRY
`recompute_milestone(p_id)` 하나에 재계산 로직을 두고 트리거·백필·디버그가 공유. 백필로 과거 클라이언트 sync의 부정합(trash-view 류)을 한 번에 보정 → 트리거가 깨끗한 기저에서 시작.

## 2. 사용자/UX

### 2-1. optimistic UI로 "체크했는데 안 닫혔다" 지연 해소
ChecklistPanel에 `optimisticOverrides` 도입 — 체크 즉시 카운트(x/N)·완료표시 반영. 회고가 지적한 인지 지연 해소. 단, **패널 국한**(다른 뷰는 refresh) — 접근법 A의 범위 합의 결과. 전 뷰 즉시 반영은 react-query 마이그레이션(별개 리팩터)이 전제.

### 2-2. "롤백" 용어의 모호성
optimistic UI의 "롤백"(화면 미리보기 되돌림)을 사용자가 "DB 진행상황/사이트 초기화"로 오해하는 순간이 있었다. → **교훈**: 기술 용어를 비개발자에게 쓸 땐 "화면 표시만 되돌림, 저장된 데이터는 그대로"처럼 풀어 써야 한다.

---

## 3. 프로세스/파이프라인

### 3-1. brainstorm→spec→plan→execute가 회고 액션에 효과적 ★가장 큰 프로세스 수홝
superpowers 파이프라인이 회고의 "다음 액션"을 단순 리스트가 아닌 **재현 가능한 실행**으로 바꿨다. HARD-GATE가 설계를 정돈하고, spec/plan이 컨텍스트 없는 실행자도 따를 수 있게 만듦. 회고 ↔ 실행 루프가 처음으로 온전히 닫혔다.

### 3-2. 자동 테스트 인프라 부재 = 인간 병목 (재확인)
DB 트리거는 `verify-milestone-trigger.sql`(ROLLBACK)로 자동 검증했지만, **UI 동작은 RTL이 없어 수동 검증**. 이건 회고(체크리스트 동기화 §2-3)가 이미 지적한 병목의 재확인. optimistic UI 동작(카운트 즉시 반영·롤백)이 자동 테스트 범위 밖이라 전부 사람 눈으로 검증.
→ **교훈**: RTL+jsdom과 DB 통합테스트 인프라는 계속 미뤄지는 부채. 회고가 반복 지적하는데 실행으로 안 옮겨지는 패턴 — 다음엔 우선순위를 올려야.

### 3-3. 2단계 분리(Phase 1→2)가 회귀 없는 분할로 적중
트리거(Phase 1)를 먼저 확정하면 optimistic(Phase 2)이 회귀 없이 분리 가능하다는 판단이 맞았다. 단계별 검증 게이트(DB 5/5 → UI 수동)가 얽힘 없이 직렬로 진행.

## 4. 환경/도구

### 4-1. Supabase direct host 비활성화 — 공식 가이드와 불일치 ★가장 시간 잡아먹은 환경 이슈
`db.<ref>.supabase.co:5432`(direct)가 신규 프로젝트에선 DNS에 없음(ENOTFOUND). 대시보드/구 가이드는 direct를 보여주지만 실제론 **pooler만 동작**. Session mode pooler(`aws-0-<region>.pooler.supabase.com:5432`)로 해결.
→ **교훈**: 공식 가이드가 인프라 변경을 따라가지 못할 수 있다. DNS 에러(ENOTFOUND)는 호스트 미지원 신호.

### 4-2. 샌드박스에 psql 없음 → Node pg로 우회
`psql` 미설치 환경에서 Node `pg` 패키지로 Postgres에 직접 연결해 마이그레이션+검증 실행. 에이전트 환경 제약을 코드로 우회하는 패턴. (단, 비밀번호 노출 부작용 — §5.)

### 4-3. 검증 SQL의 PERFORM 버그 — 자동 실행이 아니었으면 놓침
`verify-milestone-trigger.sql`에서 `PERFORM`(plpgsql 전용)을 최상위 SQL에 써서 에러. 라이브 DB 자동 실행 끝에 발견. 수동 검증이었으면 프로덕션 적용 후에 봤을 것.
→ **교훈**: 검증 스크립트 자체도 버그 낸다. 자동 실행 파이프라인이 이걸 잡아냄 — "자동 검증 우선" 원칙의 가치.

## 5. 보안

### 5-1. 자격증명 채팅 노출 ★가장 뼈아픈
OAuth `client_secret` 파일이 루트에 방치(루트 `.gitignore` 자체가 없었음) + DB 비밀번호가 작업을 위해 채팅에 노출. gitignore 추가로 예방했지만, **채팅에 찍힌 DB 비밀번호는 재설정 필요**(사용자 액션, 작성일 기준 미확인).
→ **교훈**: 에이전트 세션에선 외부 자격증명을 환경변수/시크릿 스토어로만 다룬다. 채팅 붙여넣기 = 로그 영구 노출. 불가피하면 즉시 폐기(재설정). "권한 있으니 다 해줘" 위임에도 보안 게이트는 분리 유지.

## 6. 내 코드의 한계 (솔직 회고)

- **optimistic override 정리를 useEffect로 짰다가 `react-hooks/set-state-in-effect` 위반**. lint가 잡아줘서 render-time("직전 렌더 props 기억") 패턴으로 수정. 최신 React 권장 패턴 숙도 부족 — effect 남용 습관.
- **검증 SQL의 PERFORM 버그**를 내가 만들고 내가 자동실행해 잡음. spec/plan 단계에선 잡지 못함 — SQL 검증 스크립트도 코드 리뷰 대상이라는 걸 간과.
- Phase 1 배포 순서(마이그레이션 먼저)를 spec에 명시했지만, 실제론 단일 DB라 dev/prod 분리가 무의미했다는 걸 실행 단계에서야 깨달음 — 설계 단계에서 "이 프로젝트는 dev/prod 분리가 있는가?"를 먼저 확인했어야.
