### 1-2. 진단: 역할 혼란에 의한 신호/잡음 역전

각 지침은 사실 3가지 문서가 한 곳에 뒤섞여 있다:

| 성격 | 예시 | 비중(체감) |
|---|---|---|
| 🔵 참고 데이터 (필요시 조회) | 25-2 단가표, 파일 경로 목록, 과거 실적, 구글폼 15문항 양식 | ~45% |
| 🟡 프로젝트 상태 (매일 변함) | D1~D7 결정 추적, 체크리스트, 마일스톤, 🟡/⚪ 상태 | ~30% |
| 🟢 진짜 지침 (기억/준수 대상) | "율전조가 1~1.5시간 먼저 세팅", "버스 23명은 상주역할과 중복 불가", "비건 필수" | ~20% |

구체적 증상:
1. **중복 폭발**: "25-2=주 템플릿(율전), 26-1=보조(명륜)" 설명이 6번 반복
2. **스프레드시트 산문 복사**: 예산팀 §5-1이 25-2 예산안 모든 라인 아이템을 단가까지 열거
3. **메타 잠식**: 마스터 §7 "갱신 가이드"는 통째로 문서 관리 매뉴얼
4. **자명/빈 섹션**: 5개 문서 모두 빈 이슈 로그, 일정 재진술 체크리스트
5. **상태 박제**: 🟡/⚪, "8/9 회의" 프레이밍이 영구 지침처럼 잔류 (8/16 이후 무효)
6. **SSOT 위반**: D4~D6 옵션표가 마스터와 예산팀에 이중 존재

### 1-3. 핵심 통찰: 상태 정보의 100%가 이미 웹앱에 존재

`sportsday-hub` 웹앱이 이미 상태 정보를 완전히 모델링하고 있음 (`lib/types/models.ts`):

| 지침 내 항목 | 웹앱 테이블 | 커버리지 |
|---|---|---|
| D1~D7 결정 추적표 | `decisions` (status/current_value/decision_date) | ✅ 완전 |
| 마일스톤·일정 | `milestones` (date/category/completed/depends_on) | ✅ 완전 |
| 진행/피드백/준비 체크리스트 | `checklist_items` (section/priority/completed) | ✅ 완전 |
| 이슈 로그 | `issues` (status) | ✅ 완전 |
| 🟡/⚪ 상태 | `DECISION_STATUS` enum | ✅ 완전 |

→ 지침의 상태 정보는 **100% 중복**이며, 웹앱이 SSOT.

## 2. 재구성 방향 (4가지 결정)

| 결정 사항 | 선택 |
|---|---|
| **데이터/참고 (80%)** | 원본 소스(엑셀/docx)에 맡기고 링크만 |
| **상태 정보** | 웹앱이 이미 완전 커버 → 지침에서 제거 |
| **팀 간 연계 표** | 웹앱 동적 렌더링(milestones.depends_on 기반) → 지침에서 제거 |
| **마스터** | 전역 원칙만 최소화 |
| **문장 스타일** | "원칙(굵게) + 이유" 혼합체 |
| **구조 접근법** | "원칙 카드" 방식 (각 카드 = 하나의 통찰) |

### 철학 요약
> **지침(마크다운) = 정적 원칙 (본질 통찰 + 템플릿 참조 링크)**
> **웹앱 = 동적 상태 (결정/일정/체크리스트/이슈) — 이미 구축됨**
> **원본 소스(엑셀/docx) = 상세 데이터 — 링크로 참조**

## 3. 공통 원칙 카드 포맷

모든 지침(마스터·팀 공통)의 원자 단위는 **3단 원칙 카드**.

### 3-1. 포맷

````markdown
## 🎯 [원칙을 명제로 요약 — 한 줄]

**원칙.** [이것만은 무조건 지킨다 — 명령형 단문]

왜: [1~2문장. 이 원칙이 존재하는 이유. 작년 무슨 일이 있었는지.]
참고: [링크] / [자세한 건 웹앱 '결정 D4' 참조]
````

### 3-2. 실제 예시

````markdown
## 🎯 게임 뼈대는 25-2(율전)를 그대로 쓴다

**원칙.** 토너먼트 4종·메인 2종·미니 6종의 뼈대는 25-2 율전 세트를 베이스로 삼고,
그 위에 인사이드아웃 컨셉을 입힌다.

왜: 25-2는 이번 26-2와 같은 장소(율전)·같은 시기(9월)·같은 버스 구조로 이미 검증됐다.
26-1은 명륜이라 장소가 달라 배치·소요시간 기준으로 부적절하다.
참고: [25-2 게임 구성 규칙.docx](../25 스포츠데이 참고용 자료/[2025_Fall_Sports Day] 게임 구성 및 규칙.docx)
````

### 3-3. 카드 규칙

| 규칙 | 이유 |
|---|---|
| 제목 = 명제 (명사구가 아닌 주장) | 스캔만 해도 핵심 전달 |
| 원칙은 1문장 | 본질만 남기기 |
| "왜:" 선택적 (있을 때만) | 지시가 아닌 설득. 작년 망고(실수)가 있을 때 특히 효과적 |
| "참고:" 링크/웹앱 참조 | 데이터 복사 금지. SSOT는 원본 |
| 상태(🟡/⚪, 8/9 회의 등) 없음 | 웹앱이 잡음 |
| 체크리스트 박스(`[ ]`) 없음 | 웹앱 `checklist_items`가 잡음 |

### 3-4. 카드 개수 가이드라인
- 마스터: 5~7개 (전역 원칙)
- 팀별: 5~8개

| **동적 상태** | 웹앱 DB | "웹앱 [D4]" 인라인 참조만 | 결정·일정·체크리스트·이슈 |
| **상세 데이터** | 원본 파일 (엑셀/docx) | 마크다운 링크만 | `[25-2 예산안.xlsx](경로)` |

### 링크 규칙 (일관성)
- 상대경로 사용: 지침 파일 위치 기준 (현재 방식 유지)
- 웹앱 참조는 짧게: `웹앱 결정 D4` / `웹앱 마일스톤` (URL은 런타임에 연결)
- 각 팀 지침 하단 **"주요 참고 자료"** 섹션에 원본 파일 링크 3-5개 집중 배치

## 9. 웹앱 파이프라인 영향 — 변경 최소

### 9-1. 파서 정합성 (`lib/markdown/parser.ts:403` `parseGuidelineSections`)

```
마크다운 → ## 분할 → EXCLUDED 패턴 필터 → JSONB sections
```

| 새 구조 요소 | 파서 동작 | 정합성 |
|---|---|---|
| `## 🎯 원칙 카드 제목` | section으로 추출 | OK |
| 카드 내 "왜/참고" 본문 | `content_md`로 저장 | OK |
| 제거한 결정/일정/체크리스트/이슈/피드백/갱신가이드 | EXCLUDED 패턴에 이미 포함 | OK |

**파서 코드 변경 불필요.** 새 지침은 기존 `migrate-from-md.ts`로 그대로 주입 가능.

> 참고: 마스터의 "행사 개요/조직도/전역 원칙" 섹션들도 `## ` 헤더이므로 파서에 의해 sections로 추출되어 웹앱에 주입된다. 이는 의도된 동작 — 기획관리팀 페이지에서 인라인 편집(Pencil 버튼)이 가능하므로 자연스럽다. EXCLUDED 패턴에 추가하지 않는다.
