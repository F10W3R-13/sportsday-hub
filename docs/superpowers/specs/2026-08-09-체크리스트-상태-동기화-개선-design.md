# 체크리스트 상태 동기화 개선 — 설계 문서

**작성일**: 2026-08-09
**대상**: sportsday-hub의 체크리스트/마일스톤 체크 상태가 여러 화면·탭에 걸쳐 일관되게 동기화되도록 개선
**상태**: 승인됨 (설계 단계 완료)

---

## 0. 배경

체크리스트/마일스톤 체크가 여러 페이지에 유기적으로 연결되어 있는지 아키텍처를 조사한 결과, **데이터 소스는 단일 테이블(`checklist_items`)로 잘 통합되어 있으나**, 상태 표시·동기화 측면에서 3가지 이슈가 확인됐다.

1. **진행률 계산 기준 불일치** — 대시보드/팀 페이지는 체크리스트 항목만으로, 타임라인은 체크리스트 + (하위 체크리스트가 없는 독립 마일스톤)을 합산한다. 같은 "진행률"이 화면마다 다른 숫자.
2. **낙관적 UI 롤백 누락** — `editable-checkbox.tsx`가 저장 실패 시 로컬 체크 상태를 되돌리지 않아, DB와 UI가 불일치한 채로 남는다.
3. **교차 탭 동기화 미흡** — `router.refresh()`는 현재 라우트만 갱신한다. 다른 탭/페이지는 새로고침 전까지 옛 값을 표시한다(`refetchOnWindowFocus`로 일부 보완되나 불완전).

**공통 원인**: 상태의 "정답"이 여러 곳에 분산되어 있거나, 실패/전파 경로가 보강되어 있지 않다.

---

## 1. 요구사항 요약

브레인스토밍을 통해 확정된 결정:

| 항목 | 결정 |
|---|---|
| 개선 범위 | 위 3가지 이슈 모두 |
| 진행률 계산 기준 | **체크리스트 항목만** (`checklist_items`). 마일스톤 자체 `completed`는 별개 표시지 진행률에 포함 안 함 |
| 계산 로직 위치 | **중앙 유틸로 통합** (`lib/utils/progress.ts`) — 진행률의 단일 출처 |
| 낙관적 UI 롤백 | 컴포넌트 수준 `onError`에서 `setLocalChecked(item.completed)` 원복 |
| 교차 탭 동기화 | **BroadcastChannel** (동일 출처 탭 간). SSR 방어 포함 |

**대전제**: 진행률 = "할 일(checklist_items) 완료율"이 가장 직관적이다. 마일스톤은 날짜별 체크포인트 개념이며, 마일스톤 산하 체크리스트가 실제 할 일이다. 마일스톤 자체의 체크(예: 단독 이벤트)는 진행률 바와 분리된 별도 표시로 둔다.

## 2. 아키텍처 개요

```
[단일 진실 공급원: checklist_items 테이블 (기존, 변경 없음)]
        │
        ├─ lib/utils/progress.ts     ← 신규: computeProgress() 단일 함수
        │     └─ 모든 화면이 호출 (진행률 정답의 단일 출처)
        │
        ├─ components/editor/editable-checkbox.tsx  ← onError 원복 추가
        │
        └─ lib/utils/broadcast.ts    ← 신규: BroadcastChannel 래퍼
              ├─ 송신: mutation onSuccess → 다른 탭에 알림
              └─ 수신: 최상위 리스너 → router.refresh() + invalidateQueries
```

데이터 테이블 구조(`checklist_items`, `milestones`)와 RLS, 감사 트리거는 **변경하지 않는다**. 이 설계는 표시 계층과 동기화 계층만 다룬다.

## 3. 이슈 1 — 진행률 계산 통일 (체크리스트만)

### 3-1. 신규 유틸: `lib/utils/progress.ts`

```ts
import type { ChecklistItem } from '@/lib/types/models'

export interface Progress {
  completed: number
  total: number
  percent: number
}

/**
 * 진행률의 단일 출처.
 * checklist_items만을 기준으로 계산한다.
 * 마일스톤 자체의 completed는 별개 표시지, 진행률에 포함하지 않는다.
 */
export function computeProgress(items: ChecklistItem[]): Progress {
  const total = items.length
  const completed = items.filter((i) => i.completed).length
  const percent = total > 0 ? Math.round((completed / total) * 100) : 0
  return { completed, total, percent }
}
```

### 3-2. 변경 지점 (3곳)

| 파일 | 현재 | 변경 후 |
|---|---|---|
| `components/dashboard/stats-cards.tsx:16-20` | 인라인 `filter/map/round` | `computeProgress(checklist)` |
| `components/team/team-tabs.tsx:30-34` | 인라인 계산 (이미 팀 필터된 배열) | `computeProgress(checklist)` |
| `components/timeline/timeline-list.tsx:91-106` | 체크리스트 + 독립 마일스톤 합산 | `computeProgress(checklistItems)` |

### 3-3. 보존 대상

타임라인 마일스톤 행의 하위 카운트(`subCompleted/subItems.length`)는 "그 마일스톤 산하 체크리스트 진행"이라는 **별개의 지역적 정보**이므로 그대로 유지한다. 정규화의 대상은 화면 최상단의 전체 진행률 바뿐이다.

## 4. 이슈 2 — 낙관적 UI 롤백

### 4-1. 책임 분리 원칙

- **mutation 훅** (`lib/mutations/checklist.ts`, `milestones.ts`): 전역 `onError`에서 toast 알림 유지
- **체크박스 컴포넌트** (`editable-checkbox.tsx`): 컴포넌트 수준 `onError`에서 로컬 상태 복구

### 4-2. 변경: `components/editor/editable-checkbox.tsx`

두 컴포넌트(`EditableChecklistCheckbox`, `EditableMilestoneCheckbox`)에 동일 패턴 적용:

```ts
const toggle = useToggleCheck()
const [localChecked, setLocalChecked] = useState(item.completed)

// item.completed가 외부에서 바뀌면(예: 다른 탭) 로컬도 동기화
useEffect(() => {
  setLocalChecked(item.completed)
}, [item.completed])

const handleChange = () => {
  setLocalChecked(!localChecked)           // 낙관적 반전
  toggle.mutate(item, {
    onError: () => setLocalChecked(item.completed),  // ← 실패 시 원복
  })
}
```

`useEffect` 동기화는 이슈 3(교차 탭)의 수신 결과로 `item.completed` prop이 바뀌었을 때 체크박스가 따라가게 하는 역할도 겸한다.

## 5. 이슈 3 — 교차 탭 동기화 (BroadcastChannel)

### 5-1. 왜 BroadcastChannel인가

- **Supabase Realtime**: 가장 견고하지만 구독 관리·연결 상태 처리 부담이 있고, 현재 규모(5팀 소규모)엔 오버스펙
- **refetchOnWindowFocus만 유지**: 탭 전환해야만 갱신 — "교차 탭 동기화"라 부르기 어렵다
- **BroadcastChannel**: 동일 출처 탭 간 전파에 충분, 외부 의존성 없음, SSR만 방어하면 됨

### 5-2. 신규 유틸: `lib/utils/broadcast.ts`

```ts
const CHANNEL_NAME = 'sportsday-sync'

export type SyncMessage =
  | { type: 'checklist-updated' }
  | { type: 'milestone-updated' }

/** 다른 탭에 상태 변경을 알린다. SSR/미지원 환경은 무시. */
export function notifyTabs(msg: SyncMessage): void {
  if (typeof BroadcastChannel === 'undefined') return
  const ch = new BroadcastChannel(CHANNEL_NAME)
  ch.postMessage(msg)
  ch.close()
}

/** 탭 동기화 메시지를 구독. 해제 함수를 반환. */
export function onTabSync(handler: (msg: SyncMessage) => void): () => void {
  if (typeof BroadcastChannel === 'undefined') return () => {}
  const ch = new BroadcastChannel(CHANNEL_NAME)
  ch.onmessage = (e: MessageEvent<SyncMessage>) => handler(e.data)
  return () => ch.close()
}
```

### 5-3. 연결 지점

**송신** — `lib/mutations/checklist.ts` 및 `milestones.ts`의 기존 `onSuccess`에 한 줄 추가:

```ts
onSuccess: () => {
  queryClient.invalidateQueries({ queryKey: queryKeys.checklist })
  notifyTabs({ type: 'checklist-updated' })   // ← 신규
  void router.refresh()
}
```

**수신** — 최상위 클라이언트 컴포넌트에서 구독. `app/providers.tsx`에 이미 React Query `QueryClient`/`router` 컨텍스트가 있으므로, 동일 계층에 리스너를 둔다:

```ts
// 신규 컴포넌트: components/sync/tab-sync-listener.tsx ('use client')
export function TabSyncListener() {
  const queryClient = useQueryClient()
  const router = useRouter()
  useEffect(() => {
    return onTabSync((msg) => {
      if (msg.type === 'checklist-updated') {
        queryClient.invalidateQueries({ queryKey: ['checklist'] })
        void router.refresh()
      }
      if (msg.type === 'milestone-updated') {
        queryClient.invalidateQueries({ queryKey: ['milestones'] })
        void router.refresh()
      }
    })
  }, [queryClient, router])
  return null
}
```

이 컴포넌트를 `app/providers.tsx`의 자식으로 렌더링하여 모든 페이지에 적용한다.

### 5-4. 자기 수신 방어

BroadcastChannel은 동일 탭의 송신을 자기 자신에게 전달하지 않는다(브라우저 표준 동작). 따라서 송신측의 기존 `router.refresh()`와 중복 발생하지 않는다. 다만 `onTabSync` 핸들러는 메시지 타입에 따라 정확히 대응하는 쿼리 키만 무효화한다.

## 7. 테스트 관점

- **진행률 일관성**: 한 체크리스트를 체크한 뒤 대시보드/팀/타임라인 세 화면의 진행률 숫자가 동일 기준으로 갱신되는지
- **롤백**: 네트워크를 의도적으로 차단하거나 RLS를 일시 거부하고 체크 → 실패 시 체크박스가 원래 상태로 복구되는지
- **크로스 탭**: 한 탭에서 체크 → 다른 탭(대시보드/타임라인)이 새로고침 없이 갱신되는지
- **SSR 안전**: `BroadcastChannel` 미지원 환경에서 렌더가 깨지지 않는지 (typeof 가드)

---

## 8. 비고

- 진행률 기준을 "체크리스트만"으로 통일함에 따라, 타임라인의 기존 전체 진행률 숫자는 (독립 마일스톤이 많을 경우) **소폭 하락**할 수 있다. 이는 의도된 변경이다 — 마일스톤 체크는 진행률이 아닌 마일스톤 행 자체의 표시로 충분하다.
- 추후 규모가 커지거나 실시간성이 중요해지면 BroadcastChannel → Supabase Realtime으로 교체 가능하다. 이때 송신/수신 인터페이스(`notifyTabs`/`onTabSync`)만 교체하면 호출부는 그대로다.
