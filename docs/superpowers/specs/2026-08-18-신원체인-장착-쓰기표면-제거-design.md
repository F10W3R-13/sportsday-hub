# 신원 체인 장착 + 죽은 쓰기 표면 제거 — 설계

**날짜**: 2026-08-18
**상태**: 승인 대기 (브레인스토밍 완료 — 핵심 결정 4건 사용자 확정)
**대상 회고 액션 아이템**: #3(sync 인가), #4(닉네임 트리거) — 공통 근본 원인 해결

---

## 배경 — 회고록을 수정하는 두 가지 코드 실상

회고록(`docs/lessons/2026-08-18-팀간-파일공유-1-2단계-회고.md`)의 #3·#4는 증상 기술이었고, 탐색 결과 근본 원인 판단이 달라진다.

1. **`save_folders`는 죽은 코드다.** 커밋 `549639d`(설정 페이지 단순화)에서 유일한 UI 호출부가 제거됐고, 현재 전체 코드베이스에 호출부가 없다(테스트만 존재). 같은 군의 `/api/drive/auto-map`(익명 → service role → 전 팀 `drive_folder_id` 재매핑 + 강제 동기화)도 호출부 0개. 살아 있는 익명 노출은 `/api/drive/sync`뿐이며 이는 드라이브→DB 읽기성 미러링이라 무결성 위험이 낮다. **따라서 "인가 설계"의 실질은 죽은 쓰기 표면 2건 제거 — 인증 인프라 불필요.**
2. **닉네임 트리거는 "유실"이 아니라 태생(8/9, 커밋 `62dfe5c`)부터 미장착이다.** `useNicknamePrompt()` 호출자가 한 번도 존재한 적이 없고(git `-S` 확인), 닉네임을 설정할 대체 UI도 없다. 감사 로그는 앱 전 역사에서 전원 '익명'으로 기록됐을 가능성이 높다. 근본 원인은 인증 인프라 부재가 아니라 **신원 수집 UI의 장착 누락 + 이를 잡을 가드 부재**다.

## 사용자가 확정한 결정

| # | 결정 | 내용 |
|---|---|---|
| 1 | 설계 방향 | **감사 강화 + 표면 축소** — 익명 열린 편집 철학 유지, 인증·권한 도입 없음 |
| 2 | 프롬프트 타이밍 | **첫 편집 시도 직전** — 열람자 무마찰, 편집자만 프롬프트 |
| 3 | 강제 여부 | **건너뛰고 '익명' 편집 허용** — 프롬프트는 넛지, 강제 아님 |
| 4 | 게이트 구조 | **ensureContext 관문화** — 모든 뮤테이션이 이미 호출하는 유일한 공통 관문에 내장 |

기각한 대안: 뮤테이션 래퍼 훅(신규 훅이 래퍼 우회 가능 — 장착 누락 재현), 컴포넌트 분산 점검(누락 방지 불가), Supabase Auth 전면 도입(규모 대비 과설계).

## 설계

### 1. 목표·비목표

**목표**
- 모든 감사 기록이 실제 닉네임을 반영 — 단, 새 기능 추가 시 장착 누락이 **구조적으로 불가능**해야 한다
- 익명 service role 쓰기 표면을 원천 제거한다

**비목표**
- 인증·권한 도입(철학 유지)
- 과거 '익명' 감사 기록 정정(수용)
- `/api/drive/sync` 인가(읽기성 미러링 + 공개 UI 버튼 존재 → 익명 수용)

### 2. 죽은 쓰기 표면 제거

- `app/api/drive/sync/route.ts`: `save_folders` 브랜치 삭제 → 라우트는 동기화 전용으로 단순화
- `tests/api-drive-sync.test.ts`: `save_folders` 케이스 제거
- `app/api/drive/auto-map/route.ts` 파일 삭제 + `tests/api-drive-auto-map.test.ts` 삭제
- `discoverTeamFolders`는 `google-callback` 라우트가 사용하므로 유지
- 폴더 재매핑 재필요 시 로컬 스크립트(`scripts/`)로 총괄이 실행 — 공개 표면 없음

### 3. ensureContext 관문화 (핵심)

`lib/supabase/client.ts`의 `ensureContext` — 모든 뮤테이션이 이미 호출하는 유일한 공통 관문 — 를 확장한다. 컴포넌트·뮤테이션 훅 수정은 0건.

```
ensureContext(client):
  1. shouldPromptNickname({hasNickname, promptedThisSession, providerReady}) — 순수 함수
  2. true면 requestNicknameViaProvider() await (설정 또는 건너뛰기까지 대기)
  3. sessionStorage 'sportsday-nickname-prompted' 마킹 (설정·건너뛰기 모두) — 세션당 1회
  4. getNickname() ?? '익명' → set_user_context RPC (기존 로직 그대로)
```

**lib↔UI 연결 (window 커스텀 이벤트, 결합 최소화)**
- `nickname-provider.tsx`: 마운트 시 리스너 등록 + 준비 플래그 설정, `nickname:prompt` 이벤트 수신 시 다이얼로그 오픈
- 다이얼로그 종료(설정·건너뛰기·Escape) 시 resolve — Promise 해소
- `requestNicknameViaProvider()`: 이벤트 발행 후 resolve 대기. **provider 미장착(준비 플래그 부재, SSR·테스트 환경)이면 즉시 '익명' 진행 — 게이트가 데드락을 만들면 안 됨**
- 대기 중 추가 호출: 모듈 수준 단일 대기 Promise 재사용 (이중 다이얼로그 방지)

**다이얼로그**: `NicknameDialog`에 '건너뛰기' 보조 버튼 추가. 취소(Escape)는 건너뛰기와 동일 취급.

**탭 간 동작**: 닉네임은 localStorage(탭 공유)이므로 한 탭에서 설정하면 다른 탭은 프롬프트 조건(`hasNickname`)에서 제외. sessionStorage 플래그는 탭별 세션당 1회.

### 4. 순수 함수 (테스트 대상)

```ts
shouldPromptNickname(input: {
  hasNickname: boolean
  promptedThisSession: boolean
  providerReady: boolean
}): boolean
// true ⟺ providerReady && !hasNickname && !promptedThisSession
```

SSR은 `providerReady=false`(window 부재)로 자연 처리 — 게이트는 클라이언트 편집 시에만 작동.

### 5. 테스트 전략

- **신규**: `shouldPromptNickname` 순수 함수 테스트 — 닉네임 유무 × 세션 플래그 × provider 준비 조합
- **삭제**: `auto-map` 라우트 테스트, `save_folders` 케이스 (죽은 코드 커버리지)
- **회귀**: 기존 테스트 전체 통과 (뮤테이션·컴포넌트 수정 0건이라 회귀 표면 최소)
- **수동 스모크** (컴포넌트 테스트 인프라 부재 — 유일한 검출망):
  1. 시크릿 창에서 임의 편집 → 프롬프트 등장 확인
  2. 닉네임 설정 → 편집 완료 → audit_log `changed_by`에 닉네임 반영 확인
  3. 재시크릿 → 건너뛰기 → 편집 완료 → `changed_by` '익명' 확인 + 세션 내 재프롬프트 없음
  4. 기존 편집 흐름(체크리스트·인계 토글 등) 정상 동작 회귀

## 성공 기준

- 편집자가 최초 편집 전 닉네임을 입력하는 경로가 존재하고, 이후 감사 로그에 닉네임이 기록된다
- 익명 service role 쓰기 엔드포인트가 코드베이스에서 사라진다
- 새 뮤테션 훅 추가 시 게이트 장착을 신경 쓸 필요가 없다 (ensureContext 관례만으로 자동 적용)
